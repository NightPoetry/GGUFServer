# 发现007 · 模拟器连跑退化四联症（风暴期抢跑/vsync冻结/输入冻结/元数据假象）

**一句话结论**：SwiftShader headless 模拟器长会话有四类退化——①克隆/冷启动后 20-25 分钟系统风暴期（dexopt+GMS 清算）内抢跑应用冷启动必 ANR；②SurfaceFlinger/vsync 管线会静默冻结（app 进程活着、主线程卡 Choreographer.getLatestVsyncEventData、screencap 挂死）；③input 管线整体冻结（input tap/swipe/keyevent 全部无效果且 adb 不报错）；④uiautomator dump 会返回陈旧缓存窗口（只含残留对话框）——解法=开机静置 20 分钟再动 + 全套守护脚本（像素定位点击、md5 变化验证、Wait 对话框自动清）。
**日期**：2026-11-12/13
**环境**：mini (192.168.3.124)，android-sdk emulator（SwiftShader swiftshader_indirect），AVD hubtest2（android-34 arm64，density 160），headless `-no-window -no-audio -no-boot-anim -no-snapshot`
**症状**：
- 应用冷启动 8-9s 后 ANR 被杀（logcat: "Killing … user request after error"），ANR 栈=main 卡 `Choreographer.doFrame → DisplayEventReceiver.getLatestVsyncEventData`（等 vsync 不至）；
- `input tap/swipe/keyevent` 静默无效（连 HOME 都不切屏），焦点 dump 显示一切正常；
- `screencap` 挂死或对同一帧重复返回（md5 不变），qemu 日志见 "Failed to find/bind ColorBuffer"、"QEMU2 CPU n thread hanging"；
- `uiautomator dump` 只返回残留 ANR 对话框窗口或旧层级；模拟器 dyld 偶发 `open() failed with errno=1`（瞬时，重试即愈）。
**根因**：SwiftShader 软渲染 + headless 模式在持续负载（模型加载 11-17 分钟 IO/CPU 重压、连续 wm size 切换、数小时连跑）下，SurfaceFlinger/vsync 与 input 通道逐渐僵死；开机风暴期系统服务（SystemUI/GMS/bluetooth）连环 ANR 抢占，此时冷启动应用撞上内存+IO 双压力必死。仓库中 GMS 循环 ANR 独立成患（com.google.android.gms/.droidguard 等）。
**解法（可复现）**：
```bash
# 0) 静音噪声源（克隆首次开机后执行一次，永久生效）
adb shell pm disable-user --user 0 com.google.android.gms
adb shell pm disable-user --user 0 com.google.android.youtube
adb shell pm disable-user --user 0 com.google.android.tts
adb shell pm disable-user --user 0 com.android.bluetooth
adb shell pm disable-user --user 0 com.google.android.apps.nexuslauncher  # launcher 陷 ANR 循环时
# 1) 开机后静置 20 分钟（风暴平息）再冷启动目标应用；期间可脚本清 Wait 对话框
adb shell svc power stayon true   # 防熄屏打断
# 2) 输入死路时的旁路：adb root 后由应用自身 uid 直启前台服务（绕过 UI 按钮与 FGS 后台限制）
adb root
adb shell run-as com.ggufserver.app am start-foreground-service --user 0 \
  -n com.ggufserver.app/.server.LlamaServerService -a com.ggufserver.app.START \
  --es modelPath /sdcard/Android/data/com.ggufserver.app/files/models/X.gguf \
  --ei port 8080 ...     # 应用必须先有前台 Activity（FGS 前台豁免）
# 3) uiautomator 不可信时用像素定位：screencap 拉回本机 → 本机 python 找 UI 色块中心 → input tap
# 4) 全部验证用 md5 变化断言（截图前后 md5 相同 = 输入未生效/渲染冻结），不信任工具返回码
```
**验证**：应用 01:48 ANR 栈（vsync 等待）+ 02:34 起 12 次输入/截图实验（md5 恒定=冻结实锤）+ 00:55 成功样本（boot 后静置 ~30 分钟 → 负载 17 分钟 → 截图成功）反向印证静置假说。
**边界与坑**：
- `settings put global hide_error_dialogs 1` 会把 ANR 对话框改为**静默替点 Close app**——模型加载类长 ANR 时应用被无声杀掉，排障时是反向坑（要保活用 0 + 守护点 Wait）。
- 服务停止时应用锁死在设置页（onBack=null 无返回路径），聊天页只有在 RUNNING 状态可达——截图流程必须先起服务。
- mini 的 python3 是 Apple shim（Xcode 许可挡死 exit 69），远端一律用 bash+uiautomator grep，像素检测拉回本机算。
- qemu 僵尸进程（UNE 状态 kill -9 不掉）会拖垮同卷 IO；AVD 整目录 `cp -rc`（APFS 克隆）秒级复制出 hubtest2 绕开被占文件。
**关联**：设计文档 06（聊天左纵栏实拍）；004（mini 工具链）；记忆卡 video-compositing/gguf-server。

## 修订 20261113 · Compose M3 抽屉 peek 几何（真凶几何学实锤）

**现象**：≥940dp 窗口下，ModalNavigationDrawer 两个抽屉在「关闭态」各露一条内容缝（左抽屉露 ~margin 宽、右抽屉同），768dp 窗口下缝宽 4dp≈不可见。全新进程、抽屉从未交互也复现——与状态无关，纯几何。
**几何实锤**：peek 宽度 ≈ 封顶列留白宽度（988 窗/760 列 → 114px；960 → 100px；768 → 4px）。M3 抽屉把 Closed 锚点算在**封顶列边缘**上（column_left - sheetWidth），而 sheet 以窗口坐标绘制——留白多大就露多少。
**解法**：
1. 截图用**留白≈0 的窗口宽**（768 宽，封顶 760 → 缝 4dp 隐形）；竖版带 768×800（恰为 1080×1124 带的 cover 比例）、横版面板 768×480（恰为 998×624 的 1.6）。
2. 需要抽屉入画时**主动开满**（点纵栏「模型配置」→ state=Open 渲染正确），顺带凑出真「三栏工作台」。
3. 修复方向（未做）：ChatScreen 的两个 ModalNavigationDrawer 显式传 `windowInsets`/自算 offset，或升级 Compose 后复测。
**教训**：uiautomator dump 在该环境会整段撒谎（返回陈旧窗口/漏节点），**一切以像素为准**——screencap 拉回本机目验+色块定位是唯一可信通道。
