# 更新日志 2026-07-25 · v1.1.4（versionCode 15）

## 本版主题：curate 切面真正开始收窄（阶段 3.5）——小模型只看见本轮用得上的工具

v1.1.3 把 `curate` 这个 join point 挖了出来，但没有任何插件用它，`exposure=null` = 全露 =
逐字节等价 v1。本版让它真的开始工作：**便签和朗读各自判断「这一轮该不该把自己的工具露给
模型」**，闲聊轮不再往 1B 极其金贵的 system 里塞工具教学。

顺手补掉三个在落地过程中暴露出来的问题（都不是新写的 bug，是"没人真的用过"才没暴露）。

### 1. SDK 补上 `gguf.hooks.curate`

阶段 3 只做了宿主侧：`PluginManifest` 认 `curate` 钩子、`Gateway` 会分发它、
`teachingClause(exposure)` 会按名收窄——但 `gguf-sdk.js` 的钩子注册表里**压根没有 curate**，
JS 侧一直是 `undefined`。插件写 `gguf.hooks.curate(...)` 只会当场抛 TypeError。

一条切面从内核到 SDK 得两头都通，这就是"没有一个插件真的用过"的代价。

### 2. 便签 / 朗读各自登记 curate 处理器

| 插件 | 露出条件（正则级快判定，禁调 LLM，150ms 预算内） |
|---|---|
| 便签 `com.gguf.notes` 1.0.2 | 隐含记录意图：`记一下/记录/提醒/待办/别忘/便签`，或「时间词 + 承诺词」（如"我下周三要去体检"、"这周五得交房租"） |
| 朗读 `com.gguf.tts` 1.1.3 | 用户在要求发声：`读一下/念给我/说出来/用语音说/read aloud`（新增 `chat:context` 权限） |

- 闲聊轮两个都不露 → 工具教学整段不注入。
- **漏判无伤**：用户显式说「帮我记一下」永远走 `route` 的确定性接管，与露不露工具无关。
- 角标朗读（用户点「朗读」）不受影响——那是 UI 侧的 `messageAction`，跟暴露集没关系。

### 3. 内核补两条纪律（§13.4）

- **弃权豁免**：暴露集 = 各处理器 `expose[]` 的并集 **∪ 没登记 curate 的插件的全部 callable**。
  否则装一个带 curate 的插件，会把第三方插件的工具静默掐掉——**不参与决策者不该被决策伤害**，
  与 fail-open 同源。为此 `CapabilityRuntime` 加了 `callableNamesOf`，内核仍然不认识
  `manifest.tools[].name` 这种 type 专属形状。
- **注入位置随表态切换（KV 前缀缓存红线）**：没人表态时，教学条款逐轮一致 → 照旧拼进首条
  system（逐字节等价 v1）。一旦有人表态，它就成了**逐轮可变**内容 → 宿主自动改插到
  「末条用户消息之前」的动态位。不这么做的话，每次意图切换（闲聊↔记事）整条 prompt 从第一个
  token 起作废，手机 CPU 要重算整段 prefill——省下的百来 token 远不够抵。
  顺带也符合实测排布结论：任务指令紧贴问题比压在最前面更容易被 1B 真正执行。

### 4. fail-open 升为分发面自带属性

`AspectBus` 的三个组合子（`routeUntilTakeOver`/`parallel`/`serialForEach`）与结果消费全部
包上 guard：处理器抛异常一律当「本轮无返回」，绝不阻断管线。`PluginRuntime.dispatch` 自己
本来就 catch，但 fail-open 是**切面自带属性**、不该依赖某个 dispatch 实现的自觉——换平台
（桌面端「小模型轮椅」进程内 JS）时新实现照样受这条纪律保护。

`CancellationException` 原样上抛：那是"调用方不要这个结果了"，不是插件故障，吞掉会让结构化
并发失效。

### 5. 重型记忆 1.0.6：召回排布 + 计算类问答两段式

- **召回块按相关度升序**：`sameTurnContinuation` 的召回块反转 bm25 降序，最相关的一条紧贴
  后面的任务指令；pageIn 同序，最相关者最后调入、在存放区里也排最后。
  （**head 本身不重排**——head 的红线是逐轮字节稳定，按当轮 query 重排会让整条 prompt 作废。
  排布结论适用于一次性组装的块，不适用于要复用 KV 的前缀。）
- **涉及计算的问题走两段式**：正则先判本轮要不要算数（求和/平均/最大/最小/计数），是则让模型
  只做「把相关数值逐条抽出来」（`json_schema` 受限解码 + temp 0 + 资料在前排布），加减乘除
  全部交给 JS。抽不到数值就退回自然语言续段，绝不硬凑一个算出来的数。
  1B 的算术不可靠，但"从文本里挑数字"很稳——把不擅长的那半外包给代码。

### 6. 新增自动化验证（真机撞不到的路径，在 Mac 上钉死）

```sh
"$GRADLE" -p android :app:testDebugUnitTest   # 19 项
node scripts/check-plugins.js                 # 26 项
```

- `AspectBusTest`（11 项）：处理器抛异常/超预算不阻断管线、取消不被吞、curate 的表态/并集/
  弃权豁免语义、收窄真的落到教学条款上。**正是 v1.1.3 真机验收里那条 ⚠️「fail-open 结构性
  已证、未现场注错」。**
- `ToolTagScannerTest`（8 项）：无标记全转发、整块标记、**逐字符跨分片零泄漏**、未声明标签名
  原样放行、4KB 证伪、finish 尾部。**正是那条 ⚠️「吞标记路径未现场触发」**——1B 不肯自发吐
  `<tool>`，但扫描器可以在 JVM 上逐字符喂。
- `scripts/check-plugins.js`：注入 mock 的 `window.gguf` 加载**真的 service.js**，跑 curate
  判定样例（便签 10 条 / 朗读 8 条）与 heavymem 计算两段式（意图判定 + 端到端算术 + 脏数据）。
  当场逮到一个真 bug：`Number(null) === 0`，受限解码偶尔给空值，不挡掉就会把"没有数"悄悄
  算成 0 污染总和/计数。
