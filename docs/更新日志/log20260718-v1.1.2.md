# 更新日志 2026-07-18 · v1.1.2（versionCode 13）

## 2026-07-19 增补：能力提供者 + 生效范围三选一（真机验证通过）

**能力提供者（§6.13，插件间的补丁式依赖，用户设计）**：插件依赖不做依赖图，只做
"既定流程上的补丁"——宿主能力点自带默认实现，插件声明 `provides:["tts"]`（权限
`cap:tts`）即接管全机发声；调用方无感知（依赖能力点而非具体插件）。核心规则：
**改道**（他人调用进提供者的 `gguf.hooks.tts` 钩子，入参带 action/from/text）、
**调穿**（提供者自己调 gguf.tts = 直达系统默认实现，可带 pitch/rate 0.5~2.0 变调
——相当于补丁里调 super()，天然无回环）、**揭补丁**（禁用/熔断/超时 fail-open
自动落回默认，预算 5s）。纯提供者插件也创建 service WebView；不入网关不破快路径。
HostTts 支持 setPitch/setSpeechRate。第 8 个内置插件「猫嗓」com.gguf.meow 1.0.0
为参考实现（句尾加喵 + pitch 1.45 调穿）。真机四项：朗读角标被接管（KV 记录
from=com.gguf.tts + 原文/加工文）✓ 变调发声 ✓ 禁用恢复原声（KV 不再更新）✓
权限弹窗「接管发声」✓。

**中间件生效范围用户三选一（§6.8 内外通用管线，用户设计）**：管线内外本就同一条，
现在把生效范围从作者写死改为用户可配——manifest `middleware.configurable: true`
（需 chat:external）即在管理页暴露「生效范围」选择器：仅对内 / 内外通用 / 仅对外
（onlyoutside）。用户选择持久化在 _state.json scopeOverrides，覆盖 manifest.scope，
activePlugins 按覆盖值过滤；不再需要为"对外"单独做一个插件。记忆插件 1.0.3 作
dogfooding 暴露此配置。真机验证：三选一渲染、仅对外→["external"] 持久化、切回正确。

**音频级变声管道（用户反馈"猫嗓听不出变化"后新增，真机验证通过）**：诊断发现
猫嗓的拦截与加喵正常（KV 有证据），但小米 TTS 引擎**静默忽略 setPitch**——引擎参数
变声在 OEM 引擎上不可靠，必须音频级处理（这正是通往 RVC 音色插件的管道）。新增：
① `gguf.tts.synthesize(text)`：HostTts.synthesizeToFile 合成 WAV 不出声，经插件
虚拟域名 `__tts__/<file>.wav` 提供（绕开桥 1MB 载荷限制）；② 插件 WebView 放开
无手势媒体播放（mediaPlaybackRequiresUserGesture=false）；③ 第 9 个内置插件
「简单变声」com.gguf.voicefx 1.0.0：提供者接管发声 → synthesize 取料 → Web Audio
解码 → playbackRate 变调（面板滑杆 0.7~1.8，存 KV）→ AudioContext 播放，失败调穿
原声保底。真机证据：播放源从小米引擎进程（uid 10206 AudioTrack）变为本 App 自身
（uid 10288 AAudio）= 声音确实经插件二次处理后播出。RVC 展望：悠米/小火龙音色插件
= 同一管道，把 playbackRate 一步换成 RVC 模型推理（可经 net:lan 调局域网推理服务）。

**定制音色插件 com.gguf.voicelab（第 10 个内置插件，2026-07-19）**：接管发声改用
真正的神经音色，三种来源：① **内置神经推理（离线）**——sherpa-onnx VITS **JNI 进程内
推理**（libsherpa-onnx-jni.so 4.4M + libonnxruntime.so 15M 进 jniLibs，官方安卓正规路径；
com.k2fsa.sherpa.onnx.Tts.kt API 原样引入）+ filesDir/tts-models/ 模型目录，首个模型
aishell3（31MB，174 个说话人 sid 选音色），桥 `gguf.tts.synthesizeLocal`。真机数据：
首句 2.6s（含模型加载），**模型常驻后 64ms/短句**——比局域网还快。
**弯路记录**：先走了静态链接 exec 二进制路线（与 llama-server 同模式），onnxruntime
1.27 与 1.17.1 都在 CreateSession 段错误（llvm-symbolizer 对未 strip 二进制定位：1.27 崩
图优化器 SelectorActionTransformer、1.17.1 崩会话创建——静态注册表被链接器裁剪的
经典病，sherpa 官方安卓从不走静态 exec）；换 JNI 共享库即愈。aishell3 纯中文模型，
英文文本无词典只出空音（换含英模型如 melo-tts-zh_en 可解）；
② **局域网 OpenAI 兼容** `/v1/audio/speech`（VoxCPM2 vLLM-Omni / Kokoro-FastAPI /
IndexTTS-2 封装等 2026 主流自建服务器）；③ **局域网 GPT-SoVITS** `/tts`（角色音色
克隆生态：英雄联盟悠米 Yuumi、小火龙 Smolder 等现成模型）。设置卡片选来源/填地址/
选音色，失败一律回退系统原声。真机验证：Mac 上起 OpenAI 兼容测试服务器（包装
macOS say·Tingting 中文音色）→ 手机点朗读 → 服务器收到请求 → 取音 973ms →
Web Audio 播放 ✓。

**新桥 `gguf.net.fetchAudio`（重要教训）**：插件页面直接 fetch 局域网服务器必撞
CORS——页面源是 https://plugin.gguf，POST JSON 触发预检，自建推理服务器普遍不回
CORS 头（首测 Failed to fetch 即此因）。宿主原生 HTTP 代取、落插件网络缓存、
经 `__net__/` 虚拟路径同源下发（≤20MB，绕开桥 1MB 载荷限制）。net:lan/net:internet
按目标主机校验。

**2026 TTS 调研结论**：接口标准收敛于 OpenAI /v1/audio/speech；服务器侧中文克隆
最强 IndexTTS-2（音色/情感解耦）、次 CosyVoice2、角色克隆生态 GPT-SoVITS；端侧
GGUF 路线 NeuTTS Air（0.5B llama.cpp 系）与 VoxCPM2（2B，llama.cpp-omni，M4 Metal
RTF 1.76 → 手机 CPU 暂不现实）；本机落地选 sherpa-onnx VITS（1~3s/句量级）。

**记忆插件更名「简单记忆」（1.0.4）**：明确三档记忆的档位定位（简单记忆=轻档
BM25 原文找回、零 LLM、唯一对外可用；线性记忆=中档闲置摘要；重型记忆=重档双模型）。
用户曾问三者是否重复——结论：目标同类、机制三档，不合并，用命名与文档写明关系。

## 本版主题：插件消息能力三连——角标、消息卡片、语音桥

### 追加：消息卡片（同日第三批，真机验证通过）

对话消息列表向插件开放「一条消息的正文区域」（用户语：给插件开放一个 div）：

- **新权限 `chat:card`** + 规范 §6.12。卡片消息 = 普通消息换了正文渲染器：**每条卡片
  一个插件 WebView**（透明背景，气泡自己画），头像/动作行/布局框架仍是宿主的、
  不可被插件改动（用户明确要求的硬边界；初版曾把头像换成插件图标，已改回），
  与普通消息在列表里自然混排。
- **交互即 DOM**：点击/长按/左右滑等全部是卡片页里的标准事件，宿主不发明回调协议。
  高度由页面 scrollHeight 经桥自动回报（与设置卡片同机制），内容变化自动跟随。
- **两条产生路径**：① 工具路径——`gguf.hooks.tool` 返回 `{card:{file?,data?}}`，
  网关经收尾 chunk 的 `gguf.cards` 扩展字段下发（外部 OpenAI 客户端忽略，零影响）；
  ② 桥路径——`gguf.card.post()` 直接插入当前会话（PluginStore.cardPosts 流 →
  ChatViewModel 落盘）。
- **内部文本约定**：`data.text` 存为消息 content——进模型上下文、可复制、导出，
  插件禁用时降级为普通文字显示（永不丢内容）。
- **生命周期纪律**：卡片 WebView 随 LazyColumn 滚动懒创建/回收，页面必须无状态可重建；
  自动副作用（自动播放）用 `data.postedAt` 判新鲜（<20s），滚动重建不重放——真机验证。
- **朗读插件 1.1.2**：新增 `tts.say` 工具 + `card.html` 语音气泡（点按播放/停止、
  长按展开文字、面板设置里可关自动播放）。真机全链路验证：面板按钮发测试卡 ✓、
  模型说 "use voice to say hello" 吐标签→吞标签→卡片入会话→自动发声 ✓、
  持久化重开会话 ✓、降级/混排 ✓。已知 1B 局限：偶尔把说明文字当原话放进标签体
  （工具描述已加「必须写原话」引导）。
- **下拉热区改回 1/4**（用户反馈 0.66 太易误触；面板拉开后的高度不变——
  拉手窄、门帘长的卷帘门不对称是刻意设计）。

## 第一批：消息角标能力开放给插件

消息下方的动作行（复制/速度/重试那排）向插件开放：插件可以在这里挂自己的角标按钮，
点击时宿主把**该条消息**交给插件处理。首个应用是内置朗读（TTS）插件——点角标发声。

### 新增

- **manifest `messageActions[]` 字段**（《工具插件规范》§2.1/§6.11）：
  `{ id, label, icon?, roles? }`。id 须以插件短名为前缀；label ≤ 6 字符；
  icon 可指定专属图标（省略复用插件 icon.png）；roles 默认仅 assistant。
- **新钩子 `messageAction`**（新权限 `chat:action`，风险级：中）：用户点角标时派发进
  service.js，入参 `{ actionId, sessionId, message: {id, role, content, reasoning, ts} }`，
  预算 10s，超时/异常计入既有熔断机制。返回值忽略——反馈由插件自己给（发声/toast/数字角标）。
- **宿主语音桥 `gguf.tts.*`**：`speak(text)` / `stop()` / `status()`，落点 Android 原生
  TextToSpeech（`plugin/HostTts.kt`）。WebView 没有 speechSynthesis，插件发声必须经宿主。
  与 ui.* 同级、不需声明权限；speak 用 QUEUE_FLUSH，后点顶掉先点。
- **第七个内置插件 com.gguf.tts「朗读」1.0.0**：`chat:action` 单权限 + `messageAction`
  单钩子的参考实现。每条消息（用户+助手）下方加「朗读」角标：点一下清洗 Markdown 后
  用系统语音朗读（代码块以「此处有一段代码」带过、表格竖线读成顿号）；再点同一条停止；
  点另一条直接切换。ui.html 是用法说明页 + 试听按钮。

### 追加：顶栏显示可配置 + 插件开发指南（同日第二批）

- **`panel.topbar` 字段**（默认 true）：false = 不占顶栏直显图标位。纯角标/纯后台
  插件（如朗读）不再白占顶栏；启动台恒列全量插件作为面板兜底入口，门户选项卡、
  手势、管理页均不受影响。朗读插件已声明 topbar:false（版本 1.0.0 → 1.0.1）。
- **`docs/插件开发指南.md`（新）**：面向第三方开发者的机制明确化文档——三分钟
  最小插件、露出面总表（哪里可见由哪个 manifest 字段控制）、manifest 全字段速查、
  生命周期、钩子/API/权限速查表、稳定性红线、调试方法、六个内置插件按形态索引、
  发布前检查清单。《工具插件规范.md》保持规范权威，指南是上手入口。

### 架构红线（不破坏既有保证）

- `messageAction` 是**纯 UI 侧钩子**：由聊天界面（ChatScreen）直接派发，不进网关管线。
  `PluginStore` 新增 `GATEWAY_HOOKS` 集合，`hasAnyMiddleware()` / `activePlugins()` 只认
  网关钩子（route/context/afterReply/continuation/params）——只声明 messageAction 的插件
  （如朗读）**不会**把网关拖出「零插件 = 裸流式」快路径。
- 角标只在消息非流式、正文非空、插件已启用且未熔断时渲染；流式期间动作行照旧不出现。

### 真机踩坑与修复

- **Android 11+ 包可见性拦 TTS 引擎**：首次真机点角标无声，logcat 见
  `AppsFilter: com.ggufserver.app -> com.xiaomi.mibrain.speech BLOCKED`——
  TextToSpeech 绑定引擎服务被包可见性过滤，且是静默失败（onInit 都不回调）。
  修复：AndroidManifest 增加 `<queries><intent><action android:name=
  "android.intent.action.TTS_SERVICE"/></intent></queries>`。
