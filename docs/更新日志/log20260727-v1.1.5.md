# 更新日志 2026-07-27 · v1.1.5（versionCode 16）

## 本版主题：两个只在「失败路径」上才现形的缺陷——head 字节抖动与冷启永久旁路

本版**没有新功能**。起因是桌面端「小模型轮椅」把同一套 §13 切面落了第二遍，反哺回四条 delta
请我们衡量要不要吸收进共享协议 v2。四条的评估结论是「全部吸收进契约文字、都不需要改代码」，
但**核对纪律 3 的过程中撞见了两个真缺陷**——都藏在失败路径里，正常跑一百遍也遇不到，
一遇到就是整段 prefill 重算或者插件永久失灵。

---

## 缺陷一：教学注入位曾随 curate 的成败逐轮抖动

v1.1.4 立的规矩是「有人表态 → 教学条款从首条 system 挪到末条用户消息之前」，为的是保住
KV 前缀。实现上写成了 `if (exposure == null) { 教学进 head }`。

问题在于 **`exposure == null` 有两种成因，性质完全不同**：

| 成因 | 性质 | 原实现的后果 |
|---|---|---|
| 没有插件登记 curate | 静态（只随用户开关插件变） | 教学进 head，正确、等价 v1 |
| 登记了但**全员异常/超时/被熔断旁路** | **逐轮可变的运行结果** | 教学也进 head → **首条 system 的字节随 curate 的成败逐轮抖动** |

第二种就是 §10 红线 5（`head` 必须字节稳定）被破的口子。抖动的那一轮、连同抖回去的下一轮，
各要重算一次整段 prefill——本机实测 169 token ≈ **1.9 秒**。而「某一轮没人表态」并不罕见：
service WebView 冷启、内存压力下的 GC、150ms 预算擦边，都会触发。

**修法**：判据从「本轮 exposure 是否为 null」改成「本次请求有没有插件**登记** curate」
（`AspectRegistry.curateRegistered`）。失败轮退化成「在动态位全露」——教学内容与原先一致，
但 head 恒定、历史 KV 不受牵连。无人登记时仍拼进 head，老路径逐字节等价。

**真机验证**（ruby `22101316C` · MiniCPM5-1B-Q8_0）：给便签和朗读都追加一个直接 `throw` 的
curate 钩子后连发三轮——三轮全部 `curate 动态教学注入 255 字（不动 head）`（255 字 = 两个工具
全露）、无 `exposure=` 行（确认无人表态），且 `cache_n=154` 在后两轮保持不变、`prompt_n` 只有
14 和 15：**head 没抖，历史 KV 全保住**。

> 诚实标注：「修复前会抖」是旧代码那一行的直接推论，没有在旧包上实拍抖动的 A/B；实拍的是修复后不抖。

## 缺陷二：App 冷启的几秒里，好插件可能被**永久**旁路

service WebView 从「创建」到「service.js 加载完」之间有几百毫秒到几秒的窗口（App 冷启时尤其
明显）。这期间 `evaluateJavascript` 打进去等于石沉大海：`__ggufDispatch` 还没定义，没人 respond，
只能干等到超时。三个后果，都不该发生：

1. 白白吃掉整个钩子预算（`route`/`curate` 各 150ms）；
2. 按「超时」记进熔断计数——**而熔断状态是落盘的**（`_state.json` 的 `bypassed`），
   冷启后连发三条请求就能把一个完全正常的插件**永久旁路**，直到用户手动恢复；
3. curate 面按纪律 3「登记了却没表态」把它的工具藏起来。

第 3 条上，纪律 3 的推理**不成立**。它的理由是「插件坏了它的 `tool` 钩子同样跑不了，教了也是
白教」——但没准备好的插件不是坏了：等模型几秒后真吐出标记时，它早就绪了，`tool` 钩子跑得动。
（这与本次从桌面端吸收的 `scope=global` 记账反转是**同一种推理错误**：把「所有者自己坏了」的
豁免理由，套到一个并非如此的情形上。见规范 §13.7(c)。）

**修法**（三处）：

- `PluginRuntime` 记录每个 service WebView 的**就绪**状态（`onFirstReady` 时置位、销毁时清除），
  新增 `isServiceReady(id)`；
- `dispatch` 遇未就绪**立即返回「本轮无返回」且不记熔断**（"没准备好" ≠ "坏了"）；
- `AspectRegistry` 把「登记了 curate 但此刻未就绪」的插件**归入弃权者**，其 callable 照弃权豁免
  保留。同时把注入位判据与就绪解耦（用 `curateRegistered`，静态），否则冷启那几轮 head 又会抖。

**真机验证**：整机冷启（force-stop → 重启 App → 启动服务）后的**第一个**被服务的请求
（+2.7s），「把这段读出来给我听」→ `curate exposure=tts.say`、`prompt_tokens=146`，工具正常
暴露；连发四轮 `bypassed` 始终为 `[]`。修复前同样流程曾观察到该轮 `exposure=(空)`、朗读工具丢失。

## 顺带：curate 收窄的**延迟**收益，第一次量出来

v1.1.4 只量了 token（闲聊轮 167→17），没量时间。桌面端反哺时指出「延迟才是用户感知，而且能
反过来证伪『判定成本吃掉收益』」，于是补量（8081 直连做分离计量 + 8080 网关确认真实路径）：

| 量 | 数值 |
|---|---|
| 全露教学条款（notes.append + tts.say） | **146 token** |
| 收窄轮 → 全露轮 prompt | **18 → 169 token** |
| 同上 prefill（各 3 次中位，`cache_prompt:false`、`max_tokens:1`） | **289ms → 1930ms，省 1641ms** |
| `route`+`curate` 稳态开销 | **≈45ms**（首轮 131ms 含 WebView 冷启） |
| **净赚比** | **≈ 36 : 1** |

手机的教学在动态位、每轮都要重算，所以省的是「每轮都省」的 prefill；桌面端教学在 head，
是「付一次头部失效换整轮变短」。两条路径都净赚，成因不同。

## 文档：规范新增 §13.7「跨宿主契约：哪些是不变量，哪些是宿主绑定」

吸收桌面端反哺的四条，做法是**把契约与宿主绑定分层**，手机侧的红线数值一个字没松：

- **(a) 预算**：契约只要求「预算是分发面自带属性 + 同步点总和小于可接受首字延迟 + 能否调 LLM
  取决于推理资源是否与本轮生成互斥」；150ms/禁调 LLM 降级为**手机绑定**（只有一个
  llama-server 实例，curate 里调 LLM 会占住马上要用来生成回复的引擎，是**自阻塞**，不是"慢"）。
- **(b) 注入位**：契约只要求「别污染被复用的前缀，并把账写下来」；「挪到动态位」是手机绑定
  （桌面端工具经 chat 模板渲染进头部，挪走会连带毁掉 GBNF 函数名白名单）。
- **(c) `scope`/`governs` 辖域**：收录契约、**手机不实现**（宿主自己不提供 callable，global 管家
  无人可管）。关键是记账方向：`own` 按「是否登记」，`global` 必须「真表态了」——照 own 的口径
  给 global 记账，管家一熔断宿主全部内置工具会凭空消失。另要求 global 管家必须声明常驻集。
- **(e) 分发面第二实现**：桌面端 `JsBackend`（JS 引擎子进程 + 双向 JSON-RPC）原样加载本规范的
  插件包，契约一行没动——「平台差异只落在 dispatch 实现里」现在有两个实现作证。

另在 §6.14 写明一条此前没写的语义：**收窄只管「教」，不管「认」与「跑」**。模型若自发吐出本轮
没露的 `<tool>`，标记照样被吞、工具照样执行（有意的 fail-open 方向）。这条**两端不同**——桌面端
靠 GBNF 白名单让收窄顺带成为硬安全边界，手机不是，别当跨宿主的共同保证。

§13.4 的内核纪律从三条变四条，新增**纪律 4「给模型看的东西必须自洽」**：暴露集算出后，凡是
「让模型知道有什么可用」的通道——教学条款、能力清单、参数 `enum`、受限解码语法白名单——都必须
用同一份，否则会出现「清单里没有、`enum` 里却有」的自相矛盾提示，小模型照着矛盾的那一半调用，
收窄反而制造了新的犯错机会。手机今天只有教学一条通道，这条暂时是空的，**阶段 4 加
`type:skill`/`type:workflow` 时立刻生效**（桌面端已在 `use_workflow`/`use_skill` 的 `enum` 上踩到）。
注意与上一段划清界限：**「执行端要不要一并拦」是宿主绑定，不是契约**。
