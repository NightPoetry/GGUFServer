# 更新日志 2026-07-28 · v1.1.12（versionCode 23）

## 本版主题：chat 模板随模型走，宿主自动适配——换 Qwen 一试就炸

用户提示「你觉得是 1B 上限的时候可以换 2B 试试」。换上 Qwen3.5-2B 第一句就出事：

```
你能发语音吗？        → HTTP 400
读一下这句话           → HTTP 400
写一段悲伤的旋律       → 正常（route 接管，那条路不注入）
```

错误原文：

> `Jinja Exception: System message must be at the beginning.`

## 根因：v1.1.4 的 KV 优化撞上 Qwen 的模板

v1.1.4 为了保住 KV 前缀，把**逐轮可变**的内容（curate 的工具教学、context 的 tail 背景块）
从首条 system 挪到「末条用户消息之前的一条独立 system 消息」。MiniCPM5 的 chatml 吃得下这种写法，
**Qwen3.5 的模板显式 `raise_exception('System message must be at the beginning.')`**。

于是在 Qwen 上：**凡是露了工具、或记忆插件注入了 tail 的轮次，整轮 400 失败**。
这不是能 fail-open 掉的小事——是用户那一句话直接报错。

## 修法：探模板能力，而不是猜模型

`--jinja` 用的就是 GGUF 里自带的那份模板，各家写法差别很大，所以宿主**探**而不是**假设**。
用 llama-server 的 `/apply-template` 在每个模型首次使用时试两个样本（按 alias 缓存，换模型自然重探）：

| 探什么 | 不支持时怎么办 |
|---|---|
| **首条 system**（`[system, user]`） | 把所有系统内容按序并进**首条用户消息**开头（Gemma 系没有 system 角色） |
| **中途 system**（`[system, user, system, user]`） | 把逐轮内容并进**末条用户消息**开头——位置一样靠后，**KV 前缀同样不受影响**（这本就是当初挪位置的目的），代价是小模型可能复述它 |

探测结论写进运行日志，用户看得见：

```
[网关] 模板能力（Qwen3.5-2B-Q8_0）：首条 system=支持，中途 system=**不支持**
       （逐轮内容将并入末条用户消息，位置同样靠后、KV 前缀不受影响）
```

探不通（如服务刚起）就当「都支持」——维持既有行为，不因探测失败改变拼法。

## 顺带回答了「为什么模型不认识自己的能力」

v1.1.11 给便签/朗读/乐句各加了一句能力条款（进首条 system、逐轮字节稳定）。在 1B 上它被无视——
问「你都会做什么」照旧背一套通用助手清单。换 2B 后，同一份提示词：

> 我什么都不会做，但我会帮你**做**所有事情。
> - **记便签**：你交代要记的事，我直接记下来，绝不推脱。
> - **发语音**：你要求用语音朗读或说话，我直接生成语音内容。
> - **作曲**：你提供旋律或想法，我直接为你创作旋律、曲子、伴奏或背景音乐。

而且 2B **自己吐出了工具标签**：

```
读一下这句话：今天天气不错  → <tool name="tts.say">今天天气不错</tool>
我下周三要去体检           → <tool name="notes.append">下周三去体检</tool>
```

这是 1B 从来做不到的（项目早有记录：1B 自发吐 `<tool>` 不可靠，所以才有「代码路由 + 受限解码」
那条确定性路径）。**所以那确实是模型档位的上限，不是管线问题——现在有对照实证。**

## 已知未修（如实记下）

工具标记的扫描与执行只在**流式**路径（`relayStreamWithScanning`）。非流式请求（外部客户端
`stream:false`）的回复里，`<tool …>` 标签会原样出现、也不会被执行。App 自己的聊天走流式，不受影响；
外部非流式客户端会看到裸标签。本版未动。
