# 更新日志 2026-07-27 · v1.1.8（versionCode 19）

## 本版主题：params 任务分档——一个「顺序按直觉排」造成的最坏方向误判

把 v1.1.6/v1.1.7 那套「带标注语料 + 指标」的方法用到第三个判定上：`params` 的任务分档
（precise 0 温 / creative 0.9 温 / chat 0.7 兜底）。

**这里的代价方向和前两个都不同**，所以第一指标也不同：

| 误判 | 后果 | 轻重 |
|---|---|---|
| precise 型 → **creative(0.9)** | **拿 0.9 的温度生成代码、算算术** | **最严重**（错答/编造） |
| creative 型 → precise(0) | 诗文干瘪重复 | 轻（用户一眼看得出，可重试） |
| 判不出来 → chat(0.7) | 中间档 | 最轻（这是设计的兜底方向） |

所以这里的第一指标是**「严重误判数必须为 0」**，而不是 recall 或 precision。

## 缺陷：`ruleClassify` 里 creative 先判、precise 后判

两张关键词表都命中时，谁在前谁赢。原实现 creative 在前，于是：

- 「写个函数生成随机**诗句**」
- 「写个脚本把**歌词**按行分割」
- 「帮我写段代码，给这些**故事**排个序」

三句都进 `temperature 0.9` —— **拿 0.9 的温度去写代码**，正好是三档误判里最坏的一种。
这不是词表不够，是**顺序按直觉排了，没按代价排**。

**修法**：precise 先判。冲突时一律偏向精确档——把诗写得干一点，远好过把代码写错。
顺带补齐算术类的同义说法（「1+2 等于几」「算算我这个月一共花了多少钱」「15% 的税…要交多少」
原先都落到 0.7 档，而算术在 0.7 温度下会算错）。

结果：调参集 **29/29**、留出集**零严重误判**（两条冲突用例都正确落 precise）。

> 过程中的一次自我纠正：为补算术我一度把正则放宽成 `算一?[下算]` 和 `一共`，留出集立刻抓到
> 误伤——「我打算**下**个月搬家」「我们**一共**聊了挺久了」都被判进 0 温度档。已收回，只留高置信写法。
> **这就是留出集的用处：它抓的是我自己刚犯的错。**

## 顺带把插件自带的 LLM 判断路径实测了一遍（结论：默认关是对的）

规则表在留出集上有 7 条漏判（同义说法覆盖不到，落中间档）。这 7 条正是插件里 `useLlm` 那条
路径要解决的，而它**默认关闭**。真机实测（ruby · MiniCPM5-1B · 打开 useLlm 跑这 7 条）：

| | 结果 |
|---|---|
| 准确率 | **7 条判对 6 条**（5 precise + 1 creative），1 条轻度偏差（「帮我起个网名」→ precise），**零严重误判** |
| 代价 | **每次判断 1150–1288ms**（中位 ~1.2s），整轮墙钟从约 2.5s 涨到约 2.2–2.3s+ |

**结论：默认关是对的，不改。** 因为「规则拿不准」的场景**本就包含所有普通闲聊**——打开之后
每句闲聊也要多等 1.2 秒，而闲聊的正确答案本来就是兜底的 0.7 档。这是个真实的用户取舍
（常写代码/算数的该开，日常聊天为主的别开），不该由默认值替用户决定。

**但设置卡里的说明是错的，必须改**：原文写「额外耗时约等于预填几十 token」——实测是 ~1.2 秒，
**低估了一个数量级**，而且成本主要在**解码标签**而不是预填。用户照着那句话根本没法做知情选择。
已按实测重写，把收益（7 条里对 6 条）和代价（闲聊也要多等 1.2s）都写进去。
