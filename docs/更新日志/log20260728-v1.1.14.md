上一版（v1.1.13）的日志第九节写了第 12 个内置插件「外援」，结尾标着 **⚠️ 真机未验**。这一版把
那句话补完：链路在真机上跑通了，同时撞出一个宿主侧的真缺陷。

先把版本账记清楚：**外援的代码写于 1.1.13 打包之后**（正式包 14:22，插件代码 15:05–15:16），

## 一、接管路径：真机通了

验收用的「外部端点」是局域网里一台机器上的 OpenAI 兼容假端点（会把收到的请求原样记下来），
这样既能看清手机往外发了什么，又不用为验收花钱。这也正是插件推荐的用法之一：端点填家里另一台
机器的地址，内容并不出家门。

手机上说「帮我写段悲伤的旋律」：

```
乐句接管 → gguf.llm.chat → llmRoute 改道 → 外援 service.js
        → gguf.net.fetchJson（宿主代取，绕开 CORS）→ 局域网端点 → 片段回来 → 照常编排成卡片
```

整轮 **1.2s**（本机 MiniCPM5-1B 编曲要十几秒），回复是「给你写了一段：Am 小调，76 BPM，悲伤，
8 小节 / 0:13，编排 A B A B」，与端点上写死的那段片段一致。端点侧收到的请求证实了四件事：

- `Authorization: Bearer <key>` 带对了；
- `temperature: 0.95` / `max_tokens: 300` 照原样透传；
- **`json_schema` 没有透传**（按设计——各家云端 API 的结构化输出参数互不相同，硬塞多半 400，
  调用方本来就有宽容解析兜底）；
- 完整的作曲 system prompt 与用户原话确实离开了手机——这正是 `cap:llm` 被标成高风险的原因。

## 二、修「不接管时没有回落」——这次验收唯一的收获

规范 §6.16 白纸黑字写着：提供者返回 `{}` = **我不接，宿主去打本机模型**。没配好、被 `only`
筛掉、超时、HTTP 错、认不出标签，全都走这条。

而宿主的 `llmRoute` 只判 `null`。`{}` 在 Kotlin 里是个**非 null** 的 JSONObject，于是这个空壳被
当成答案交给了调用方——调用方多半没有「空壳」这个分支。

真机复现：把外援配成「只服务便签」（乐句被筛掉），再说同一句「帮我写段悲伤的旋律」：

| | 结果 |
|---|---|
| 耗时 | 0.28s |
| 外部端点收到的请求 | **0 条**（对，它本来就不该接） |
| 本机模型 | **压根没被问过** |
| 用户看到的 | 「这次没写出能用的片段，要不换个说法再试试？」 |

**打开一个保底插件，反而把原有能力弄丢了**——正是保底最不该有的失败方向，而且它安静得很：
没有报错、没有日志、没有熔断，只是能力凭空消失了（这个项目已经为「能力静默丢失」查过好几次）。

修法是把判据从「它有没有回话」改成「**它有没有交出这次调用要的东西**」：`chat` 看 `content`、
`classify` 看 `label`，空壳一律回落本机。这一支不写日志、不记熔断——主动不接是常态（用户只勾了
某几个插件走外援），逐轮刷日志没有意义。

**注意发声（§6.13）的 `{}` 含义正好相反**：那边的提供者（变声 / 悠米音色）是**自己把声音放完**
再返回 `{}`，表示「已处理」；这边的提供者只是个中转，不交出内容就等于什么都没发生。同样是空对象、
两个能力点的含义相反，所以 `ttsRoute` 保持原样，没有跟着改。

## 三、自检

JVM 单测 31 → **39 项**（新增 `LlmProviderRouteTest` 8 项），把这条纪律钉在编译期：空对象 / 只有
无关字段 / 空 label / 空 content 都算没接管，给了 content 或 label 才算接管，未知动作向前兼容。

理由是这条纪律**靠肉眼看不住**——`{}` 与 `{content:"…"}` 在类型上毫无区别，代码读起来都对。

`node scripts/check-plugins.js`（插件侧 16 条断言）照常全过：插件那一半本来就是对的，返回 `{}`
的方向从一开始就没错，错的是宿主怎么理解它。
