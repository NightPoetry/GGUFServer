# v1.1.13（2026-07-28）—— 乐句能导出 .mid；route 判定改两段式：关键字管召回、LLM 管精度

本版全程用 **Qwen3.5-2B-Q8_0** 在真机（Redmi ruby / Android 14）验收。1B 上工具协议本就不通
（v1.1.12 已记），这次的判定实验也只有 2B 能做。

---

## 一、乐句导出 `.mid`（新能力点 `files:save`）

插件跑在 WebView 里，算得出 `.mid` 的字节，却**没有任何通道交给用户**（`data:` URL 下载在
WebView 里不可靠、`storage` 只存 JSON）。所以宿主补第 15 个能力点：

- `gguf.files.saveDownload({name, mime, base64})` → 写进系统「下载」。API 29+ 走 MediaStore
  Downloads 集合，**不需要任何运行时权限**；更老的系统退回公共下载目录。8MB 上限、文件名消毒、
  同名不覆盖。
- 乐句 1.3.x 据此加「下载」消息角标（与朗读同一行），把乐句编成**标准 MIDI**：SMF format 1，
  轨 0 只放速度元事件，其余每轨一个 GM 音色。音符模型本来就是 MIDI 语义（音高 0–127、力度、
  以 tick 计时长），编码只是写成字节。

真机验收：点角标 → `/sdcard/Download/乐句-C-100bpm-07281202.mid`，`file(1)` 认作
`Standard MIDI data (format 1) using 3 tracks at 1/480`。自检里正经解析写出来的文件（魔数、
format、division、note-on/off 配平且等于音符数、速度元事件、末 tick = totalTicks）。

## 二、route 判定改两段式（§6.2.1）—— 用户提议的方向

手写关键字枚举补不完：乐句为「写…音乐」栽过三次（先漏「调」，再漏「音乐」——`写…` 分支的宾语
集合里偏偏没有它，于是模型自己去写了个 HTML 播放器）；而一放宽又会把「写个音乐播放器」误接管
成作曲。§6.14 早就写下天花板：**正则吃得下句法、吃不下语义**。这版正面解决：

- **快判定**（150ms，仍只准跑正则）分三档：高置信说法直接接管（零成本）；有音乐味但拿不准的
  返回 `{ deep: true }`；毫无音乐味的一分钱不花。
- **深判**拿独立预算（6s，不占 route 的 150ms——那 150ms 是给扫正则的，跟问模型差两个数量级），
  调一次 `llm.classify`。真机稳态 2.1–2.5s，只落在命中关键字的少数轮次上。
- fail-open 方向按 route 纪律：判不出来**不接管**（漏了模型自己还能答，误接管是整轮被替换）。

真机端到端（分档经第六节的评测修正后）：

| 说的话 | 走哪条 | 结果 |
|---|---|---|
| 写一段悲伤的旋律 | 快判定 | 接管，Cm 小调 62 BPM（零判断成本） |
| 帮我写个欢快的音乐🎵 | 快判定 | 接管（第一版曾把它降级给 LLM，被判成「闲聊」，见第六节） |
| 写个音乐播放器 | 快判定（代码语境硬否决） | 不接管，模型去写播放器 |
| 这首歌真好听 | 深判 → 闲聊 | 不接管，正常闲聊 |
| 我想要一段适合睡前听的音乐 | 深判 → 旋律 | 接管——「想要」不在动词表里，这条是深判救回来的 |

### 顺带量出来的两条判定纪律（都写进了 §6.2.1）

- **不要用是非题**。「是不是要作曲」这种二选一上，模型答什么几乎只取决于选项怎么排——同一批
  用例把 labels 顺序一换，答案全跟着变。改成「他想要的是哪一类？」的多选（代码/旋律/闲聊/知识，
  第一个字就不同）后判得准多了。
- **受限解码在 2B 上会毒化判断**。`json_schema` 顶层 enum 是 1B 上验证过的做法，换到
  Qwen3.5-2B 上完全没有区分力；用 object schema 让它「先写理由再给结论」时，**理由完全正确、
  结论仍然选错**（「用户请求创作欢快音乐，属于创意生成任务」→ 结论「代码」）——GBNF 把第一个
  token 钉死了，模型没有「想」的余地。同样六条用例改成不受限、只回一个词：**5/6 正确、1.1s**。
  所以 `llm.classify` 改成先自由生成再解析标签，受限解码只当保底（老模型上仍然稳）。

## 三、修「开 App 说的第一句话丢接管」——真凶是 route 面预算

真机反复撞到：App 刚起来（或从别的 App 切回来）说的第一句「write a midi song」不接管，第二句
就正常。先后试了两个方向，最后靠**新加的日志**才定位到真凶：

```
[网关] route 面预算已见底（150ms），本轮没轮到：com.gguf.midi（它们的接管能力本轮缺席）
```

不是插件没就绪，是 **route 面 150ms 被排在前面的插件吃光**——App 刚起来主线程还在渲染 Compose，
一次 WebView 往返要 190ms（稳态只要 45ms），排在后面的乐句永远轮不到。三处修改：

1. **route 面预算见底改为保底补问**：再给每个没被问过的处理器一次 250ms（一次冷往返的实测上界），
   保底总上限 500ms。理由是代价不对称——漏接管 = 整轮能力消失，多花的是几十毫秒首字延迟。
2. **route 面的静默跳过留痕**（curate 面 2026-07-27 已补，route 面一直漏着，这次为定位它多花了很久）。
3. **就绪宽限覆盖 WebView 重建**：原先只等「从没就绪过」的插件，而切后台再切回来系统会回收
   WebView；现在重建中的也等（给一半预算）。

## 四、其它两个真机缺陷

- **消息卡片展开后收不回去**（用户报）：长按乐句卡片看音符会把下面的「复制/朗读/下载」推下去，
  再收起时卡片不缩回、留一大块空白。根因在 SDK 的高度回报量的是 `documentElement.scrollHeight`
  ——宿主把 WebView 高度设成上报值之后，它至少等于视口高（被 WebView 自己撑着），「内容变矮」
  永远报不回去，连 ResizeObserver 都不再触发。改成量 body（block 盒，高度随内容缩得回去）。
- **`llm.classify` 在 Qwen 上一直是废的**：它把判断指令挂成一条末尾 system，而 Qwen 模板禁止
  中途 system → 整个判断请求 HTTP 400 → 判断静默失败。v1.1.12 只修了网关的注入位，classify 是
  第二条路径，同一个坑又踩一遍。根因是「模板能力」这个客观事实没共享，现在抽成 `TemplateProbe`
  由网关与插件桥共用，并在服务就绪时预探（否则第一次探测会落进某个请求的预算里）。
- **notice 不再硬套便签的措辞**：notice 是所有插件共用的通道，旧代码给不以「已/便签」开头的一律
  加「已记入便签：」前缀，于是真机上出现了「已记入便签：这段乐句没认出可用的音符」。

## 五、自检

- JVM 单测 24 → **31 项**：route 两段式 4 条纪律（已接管就不再深判、没给深判预算则忽略申请、
  深判预算见底不派、深判带 deep 标记）+ 保底补问 2 条（保底能补到、保底也用尽才真不叫醒）。
- `node scripts/check-plugins.js`：新增 route 三档分流 13 条 + 深判分支 5 条（含「快判定这一遍
  绝不许调 LLM」硬门）+ 导出 .mid 的 SMF 结构解析。

## 六、补做：给判定建语料和指标（新增 `scripts/bench-route.js`）

上面那些结论最初只有四五条手挑用例撑着，而规范 §6.14 自己写着「改判定前先跑带指标的语料」。
所以补了一个**真机评测脚本**：加载真的 service.js、走真的 route 钩子、深判用与宿主
`llmClassify` 同构的构造打真模型，输出调参集与泛化集两组 recall/precision。

一量就翻了两个案子：

**① 乐句的第一版分层是错的。** 想当然地把「音乐」「歌」这类歧义大的词整个降级给 LLM，结果
「写一段音乐」「创作一首歌」「给我整首歌」被判成「闲聊」——recall 77%、precision 91%
（「做一个音乐网站」被判成「旋律」→ 误接管）。教训：**别把正则已经判得准的东西交给判不准的模型**。
重排后：`musicRe` 命中且无代码语境 → 直接接管；有代码语境 → **正则硬否决**（不问 LLM，实测它在
这一档上不可靠，而误接管是整轮被替换）；只有音乐味没有「要一段」的结构 → 深判。
**调参集 100%/100%、泛化集 100%/100%**，深判平均 577ms。

**② 便签的 recall 只有 38%。** 1.0.4 那次「收紧」把误接管压到 0 是真的，但 recall 从没量过。
「便签里加一条：周五交房租」「便签里那条房租的，帮我改成周六」「记一下我的车牌是京A12345」
统统不接管——三个类别缺口：动词表只有「改/删」没有「增」、记录意图强制要求「帮我/给我」前缀、
动词必须与「便签」句法相邻。便签 1.0.7 改成两段式（宽门闸「含便签 ∧ 含增删改动词」→ 深判把关，
硬前提仍是句子里有「便签」，最坏情况限定在用户确实提到便签的轮次）：**调参集 38% → 100% recall，
precision 保持 100%**。

**③ 顺带量出最关键的一条提问纪律：问宾语，别问意图。**
便签深判第一版问「他是要改便签，还是在聊这个功能」——9 条只对 4 条，§6.2 记下的那四条「谈论便签」
全被判成「要改」（它们都是复合句，「我想**改**一下我的工作流」里的动词指向别的东西）。
改成问「这句话里，用户真正要改动的**东西**是什么？」（便签内容／别的东西／没要改／在打听）——
**9/9 全对**。乐句那边的「他想要的是哪一类」好使是同一个道理。已写进 §6.2.1。

另外记一条诚实的观察：**深判有波动**，同一条用例先后两次可能给不同标签。所以它是**补召回**的，
不是主判据——能用句法钉死的仍然要钉死。

## 七、curate 面也加了保底

真机日志里冷启第一轮 `tts` 和 `midi` 一起被跳过，那一轮模型手里没有任何工具教学。与 route 同一个
成因（一次冷 WebView 往返 250ms 就能吃光 150ms 预算），所以同样给保底，但额度只有 route 的一半
——curate 漏掉只少露几十 token，且弃权豁免会把它的工具照常放出去，代价小一个数量级。

插件版本：乐句 1.3.3、便签 1.0.7。
