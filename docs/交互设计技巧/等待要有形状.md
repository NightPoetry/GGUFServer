# 等待要有形状：让用户等，就要让他知道在等什么、等到哪了

## 本质

等待的煎熬主要不来自时长，来自不确定——不知道系统死没死、不知道还要多久、
不知道等完会得到什么。给等待一个"形状"（先给一部分结果、说明正在干什么），
同样的时长，体感完全不同。

## 例子

重型记忆插件的两段式续写。手机是纯 CPU 推理，如果等后台检索完历史记忆再开始
回答，用户要对着空白等十几秒。实际方案是：前台模型先立刻流式作答（可能记不全
细节），第一段流完之后，消息下方出现一条「正在回忆…」的提示，几秒后检索结果
以衔接文字续写在同一条消息里。用户的体感是"它马上回答了我，然后想起了更多"——
而不是"它卡了十几秒"。

小处同理：插件接管对话回合时，占位消息上有插件报告的进度文案（"正在整理便签…"）；
生成中的消息旁有实时刷新的 token/s 速度——都在告诉用户"活着，在干活，干到这了"。

## 分析

两段式的关键取舍是"先给一个不完美的即时结果，还是憋一个完美的迟到结果"。
交互上几乎总该选前者：即时的第一段建立了"系统在响应"的确定性，后面的等待就
从"悬着"变成了"追加"，心理时钟完全不同。前提是要诚实——「正在回忆…」明确告诉
用户第一段可能不全、还有后续，用户就不会拿第一段当最终答案。

反面教材是通用转圈：它只说"在忙"，不说在忙什么、忙到哪，形状最弱。文案哪怕
只具体一点（"正在回忆"而不是"加载中"），确定性就多一分。
