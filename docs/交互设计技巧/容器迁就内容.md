# 容器迁就内容：由内容决定容器多大，容器绝不裁剪内容

## 本质

固定尺寸的容器是在替未来的内容打赌，赌错的表现就是裁切——控件显示一半、
文字被截断、滑块拖不到头。内容是变量，容器就必须是函数：高度永远由内容算出来，
不足一屏自然收缩，超过一屏交给滚动。

## 例子

插件设置卡片的高度打过两次脸。第一版固定 340dp，重型记忆插件的设置（模型选择
加几条滑块）超高被裁，用户反馈"存放区大小滑块被剪切出去显示不完全"。第二版
改成自适应但"留了个心眼"加了 560dp 上限，结果同一个插件的长设置照样被裁到
「手势唤出」区域整段看不见。最终版本才彻底想通：内容多高卡片就多高，不设任何
上限——外层本来就是可滚动的页面，卡片再高也滚得到底，上限从头到尾是多余的。
配套动作是展开时自动把该插件那一行滚到屏幕顶端，长卡片从头看起。

消息列表也是同一条原则的另一面：不足一屏的短对话，列表按内容高度从顶部自然
排列（用户发现过反例："第一条消息怎么到了最下面？"——fillMaxSize 让短对话
贴到了屏幕底部）；超过一屏才撑满、启用底部锚定。

## 分析

裁切是最没有借口的界面缺陷：它不是风格问题，是内容的丢失，用户既看不到
也没有任何办法看到。而"设个上限保险"的直觉恰恰是错的——上限就是下一次裁切的
预约。正确的保险方向不是限制内容，而是保证滚动：只要外层能滚，内容多高都
到得了；一旦靠上限兜底，就总有一天兜不住。
