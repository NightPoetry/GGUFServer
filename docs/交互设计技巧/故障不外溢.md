# 故障不外溢：内部的失败在内部消化，交给用户的最多是"稍等了一下"

## 本质

组件可以失败，体验不能失败。故障处理的目标不是"报告得清楚"，而是把冲击
限制在最小范围：能自动恢复就自动恢复，能降级就降级，用户感知到的最坏情况
是"慢了一拍"或"这个功能像没装一样"，而不是崩溃、卡死、数据丢失。

## 例子

三层防线，各管一段：

GPU 崩溃自动回退——某些机型上 GPU 推理会直接崩，服务检测到后自动改用纯 CPU
参数重新拉起，对用户表现为"稍等一下又好了"，而不是 App 闪退。搭配「最优引擎
测评」按钮，把"该用 GPU 还是 CPU"这种试错也替用户做掉，不让用户拿崩溃换经验。

插件熔断——某个插件连续三次超时或出错，它的所有钩子自动旁路，顶栏亮一个红点，
管理页能看到错误详情并一键恢复。一个写坏的插件最多让自己失效，拖不慢对话。

网关 fail-open——插件管线出任何异常都不阻断请求转发，最坏情况等于零插件透传，
对外的 API 永远可用。配套的数据底线：内置插件只能禁用不能卸载，因为卸载会清空
私有数据而下次启动又会释放一个空插件回来——等于借"卸载"之手悄悄清了用户数据。

## 分析

这些机制的共同点是失败的代价被就地吞掉，不沿着调用链往用户那里传。设计时
先问"这一层挂了，用户会看到什么"，答案必须是以下三种之一：看不到、慢一点、
这个功能暂时没了——绝不允许是"整个应用不能用了"或"数据没了"。

红点和错误详情同样重要：消化故障不等于隐瞒故障。用户不被打扰，但想追查时
一切都在——"默默扛住，如实记录"，两件事一件都不能少。
