# 设计文档09 · 多模态支持提案（视觉输入/语音输入/语音输出）

## §0 设计原话（逐字）
> 「对了，有一些模型它支持多模态。你必须让你也支持多模态，比如说语音输入、语音输出、视觉输入等等。」（2026-11-17）
> 「注意保存好版本，让我随时可以回滚。」（2026-11-17）
> 「注意 UI 的设计，一定要符合之前的设计哲学，不要很突兀。」（2026-11-17）

## §1 语义提炼
让 App 具备多模态交互能力，分三条能力线：视觉输入（发图片给多模态模型识别/描述/问答）、语音输入（说话转文字或直接音频转写）、语音输出（回复朗读出来）。三条线独立可用、逐期交付；UI 严格沿用现有设计语言（暖色调卡片/胶囊/纵栏），不引入突兀控件。

## §2 技术底座盘点（项目已有资产）
1. **服务端（已具备，发现001）**：llama-server v0.8.0 嵌入端点多模态能力——`/v1/chat/completions` 支持图片输入（OpenAI `image_url` 形状，base64 data URL），`--mmproj` 与 `--embeddings` 可同用；llama-bench/多模态联合池化已有源码证据链。**视觉输入的服务端零开发**，只欠客户端 UI 与 mmproj 配对逻辑。
2. **客户端原生库（已具备）**：jniLibs 里 onnxruntime 与 sherpa（rebuild.sh 清理白名单明确保留）——sherpa-onnx 提供 ASR（流式识别）与 TTS（离线合成）两条线的运行时；缺的是模型资产与接线。
3. **mmproj 配对（数据面）**：多模态模型仓库自带 mmproj-*.gguf（视觉投影），模型市场 tree 解析已排除 mmproj（不进量化列表）——需在下载时识别并提示随本体一起下载，形成「本体+mmproj」配对记录。

## §3 分期路线（每期独立可交付）
### 一期 · 视觉输入（v1.2.0）
- 聊天页输入卡新增「图片」按钮（相机拍摄/相册选择，系统 ActivityResult）；图片本地压缩后转 base64 data URL，按 OpenAI `image_url` 形状并入 messages 发送。
- 模型市场：mmproj 文件在量化展开面板显示为「视觉投影（随本体下载）」条目（不再简单隐藏），一键随本体配对下载；选中模型带 mmproj 时自动挂 `--mmproj` 参数拉起。
- 不支持视觉的模型（无 mmproj）：图片按钮隐藏/置灰提示「当前模型不支持视觉输入」。
- UI：图片按钮走现有输入卡右侧按钮体系（34dp 同款）；已附图片以缩略胶囊显示在输入框上方，可删除。

### 二期 · 语音输入（v1.2.1）
- sherpa-onnx 流式 ASR：输入卡新增「语音」按钮（按住说话/点击开始-结束），识别文本进输入框（可编辑后发送，而不是直接发出——保留用户控制权）。
- ASR 模型（如 sherpa-onnx zipformer 中文小模型）走模型市场同款下载器（断点续传/多线程复用）。
### 三期 · 语音输出（v1.2.2）
- sherpa-onnx 离线 TTS 或系统 TTS 双通道：消息气泡加「朗读」角标（沿用现有角标体系 requiresCard 机制）；设置页「语音输出」组（音色/语速/开关）。
### 回滚保障
- 每期发正式包时 release.sh 自动打 `release/vX.Y.Z` 锚点 tag + APK 归档（已生效）；`git checkout release/vX.Y.Z` + 对应 APK 即可整体回滚。

## §4 关键决策 Why
1. 视觉输入一期先行：服务端零开发、客户端工作量最小、用户可感知价值最高（拍照问模型）。
2. ASR 用 sherpa-onnx 而非云 API：项目定位=本地私有部署（数据不出手机），离线优先是产品底线。
3. TTS 三期且双通道：离线 TTS 模型体积大（几十 MB~百 MB 级），先用系统 TTS 快速可用，离线音色作为增强。
4. mmproj 配对而非自动下载：mmproj 由模型作者配对发布，自动猜配对易错；UI 明示配对关系让用户知情。

## §5 验证方案（每期）
- 一期：MiniCPM-V 类多模态模型 + mmproj 实拍图片问答闭环；非多模态模型图片按钮置灰；OpenAI 形状请求 dump 与 llama-server 日志交叉验证。
- 二期：中文短句识别准确率抽样；断网识别（离线性验证）。
- 三期：朗读触发/停止、后台播放行为；TTS 与流式回复的时序（流式完成后朗读）。
