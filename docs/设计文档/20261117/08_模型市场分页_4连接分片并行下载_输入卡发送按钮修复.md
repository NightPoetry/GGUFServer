# 设计文档08 · 模型市场分页、4连接分片并行下载与输入卡发送按钮修复

## §0 设计原话（逐字）
> 「我还发现模型市场没法翻页，导致只能看到一部分推荐模型，我还发现没有多线程自适应下载导致下载速度比较慢」（2026-11-16）
> 「我发现模型名太长的时候会导致输入框的发送按钮消失」（2026-11-17）

## §1 语义提炼
三件事：①热门/搜索列表接入 HF 分页（此前固定 limit=30 只能看前 30 条，触底无后续）；②下载改多连接并行（此前单连接 HttpURLConnection，hf-mirror 单连接限速明显）；③聊天输入卡模型名过长把发送按钮挤出屏幕（点不了发送=功能不可用）。

## §2 算法/数据/接口
1. **分页（HubApi + HubState）**：`listPopularUrl/searchUrl` 增 `skip` 参数（skip>0 才追加 `&skip=`，skip=0 保持旧 URL 与既有单测兼容）；`HubState.loadMore()` 以 `rows.size` 为 skip 拉下一页，`known` 集合按 id 去重后追加，返回空即 `endReached`；新增判定循环（与 load 同款：逐仓 judge 回填/失败打 failed 标）。
2. **多线程下载（ModelHubDownloader）**：`downloadTo` 改分派——`total ≥ 8MB` 走 `downloadMulti`（4 连接，区间均分 `[i*per, (i+1)*per-1]`，末片收尾），每分片独立文件 `<part>.0..3`（长度=已收字节，天然断点）、Range 请求 `bytes=<from+have>-<to>` 固定右端；`coroutineScope` 内 4 分片协程+1 ticker 协程（600ms 聚合 received/EMA 速度）；分片收到非 206（服务器不支持 Range）即抛错走单线程回退 `downloadSingle`（原实现，200 全量回零逻辑保留）；全分片长度校验后顺序合并为最终文件并删分片。单线程旧路径完整保留（<8MB、分片失败回退、未知大小）。
3. **Composer（ChatScreen.kt）**：模型名 Text 加 `Modifier.weight(1f)`、删除 `Spacer(weight(1f))`——weight 子项在固定子项（34dp 发送钮）之后测量，长名 Ellipsis 让位，按钮永不被挤出。

## §3 关键决策 Why
1. 分片间共享单 .part 改为每分片独立文件（.part0..3）：单文件无法表达「各分片各自进度」，独立文件让断点续传语义分片粒度保留；合并后删分片，不占额外长期空间。
2. 4 连接而非更多：手机蜂窝/WiFi 场景 4 连接已近带宽饱和，更多连接对镜像站不礼貌且收益递减。
3. 触底自动加载而非「下一页」按钮：列表语义（浏览热门榜）更适合无限滚动；「已经到底了」显式提示防无限空拉。
4. Composer 用 weight 而非给发送按钮加权重排：weight 子项后测量的 Compose 语义天然保证固定按钮优先占位。
