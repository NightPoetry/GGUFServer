## 桌面端反哺的四条：吸收决策（2026-07-27）

桌面端把同一套 §13 切面落了第二遍（`小模型轮椅/设计/切面微内核-轮椅落法.md`，2026-07-26），
反哺回四条 delta。逐条判过，**四条全部吸收进契约文字，四条本身都不需要改代码**（核对纪律 3 时
另外撞见一个真缺陷，见下节「教学注入位曾随 curate 的成败逐轮抖动」——那是本轮唯一的行为改动）：

| 反哺条目 | 决策 | 落点 | 为什么不写代码 |
|---|---|---|---|
| `scope`/`governs` 辖域 + **own/global 记账相反** + 常驻集兜底 | ✅ 收进契约，**不实现** | §13.7(c) | 手机今天**没有主体**：宿主自己不提供任何 callable，每个 callable 都属于一个能自己表态的插件，global 管家无人可管。实现即死代码（同「阶段 4 不预置空壳」的纪律）。但契约必须现在写——照 own 口径给 global 记账会让「管家一熔断，宿主全部内置工具凭空消失」，这是靠单测才发现、真机撞不出来的坑 |
| skill/workflow 运行时接口 = 三个真样例验证 | ✅ 吸收，**接口不动** | §13.5 末 · §13.6 阶段 4 · `ToolRuntime.kt` 注释 | 结论是「别动」而不是「可以上提了」：三个 runtime 的执行面天然分叉，stream/after 上提会造出谁都不合身的形状。原先的「怕抽错抽象」顾虑作废 |
| curate 要连**延迟**一起量 | ✅ 吸收 + **手机侧已补量** | §13.7(d) · §13.6 验收红线 ⑤ | 见下节实测：省 1641ms、判定成本 45ms，净赚 ≈36:1 |
| 预算与注入位「同一契约、两套绑定」 | ✅ 吸收，把不变量与绑定**分层写** | §13.7(a)(b) · §10 红线 2/5 加注 · §13.3 加注 | 手机的 150ms/禁调 LLM、动态注入位**保持原样不变**——它们从「契约条款」降级成「本宿主绑定」，红线本身一个字没松 |

两处必须记住的**反向**结论（容易被后人「顺手改错」）：

1. **手机的 150ms + 禁止调 LLM 不是「慢就不许」**，是结构性的：只有一个 llama-server 实例，
   curate 里调 LLM 会占住马上要用来生成本轮回复的引擎（自阻塞）。桌面端有独立 preflight 闸门
   才给得起 25s。**降级为宿主绑定 ≠ 手机可以放宽。**
2. **「教学挪到动态位」是手机绑定，别拿去改桌面端**：那边工具经 chat 模板渲染进头部（原生
   `tool_calls`），挪走会连带毁掉同一份 schema 生成的 GBNF 函数名白名单。

## 修复：教学注入位曾随 curate 的成败逐轮抖动（2026-07-27，未发版）

**这是上面那轮反哺评估里唯一真找出来的代码缺陷**，不是桌面端提的四条之一，是核对纪律 3 时撞见的。

`Gateway.applySystemSuffix` 原先用 `exposure == null` 决定教学注入位。但暴露集为 null 有**两种**成因：

| 成因 | 性质 | 原实现的后果 |
|---|---|---|
| 无人登记 curate | 静态（只随用户开关插件变） | 教学进 head，正确、等价 v1 |
| 登记了但**全员异常/超时/被熔断旁路** | **逐轮可变的运行结果** | 教学也进 head → **首条 system 的字节随 curate 的成败逐轮抖动** |

第二种就是 §10 红线 5（head 必须字节稳定）被破的口子：抖动的那一轮 + 抖回去的下一轮各要重算
一次整段 prefill（本机实测 169 token ≈ 1.9s）。而 curate 处理器偶发失败并不罕见——service WebView
冷启、内存压力下的 GC、150ms 预算擦边，都会让某一轮无人表态。

**修法**（`Gateway.kt`，三处）：判据从「本轮 exposure 是否为 null」改成「本次请求有没有插件**登记**
curate」（`reg.curate.isNotEmpty()`）。失败轮退化成「在动态位全露」——教学内容与原先一致，
但 head 恒定、历史 KV 不受牵连。无人登记时仍拼进 head，逐字节等价 v1 的老路径不动。

**真机验证（同上设备，同一批测）**：

| 场景 | 结果 |
|---|---|
| 回归：正常收窄三轮 | `prompt_tokens` 18 / 89 / 146，`curate exposure=(空)/notes.append/tts.say`，动态注入 125/202 字——与修复前逐项一致 |
| **注错：给 notes + tts 都追加 `throw` 的 curate 钩子** | 三轮全部 `curate 动态教学注入 255 字（不动 head）`（255 字 = 两个工具全露），**无 `exposure=` 行**（确认无人表态）；`cache_n=154` 在后两轮保持不变、`prompt_n` 仅 14/15 → **head 没抖，历史 KV 全保住** |
| 恢复 | 两个 `service.js` md5 与改前一致；`_state.json` 的 `bypassed` 清回 `[]`（注错把 tts 熔断了，且熔断状态会落盘——**这点下次注错前要记得**）；恢复后 18 / 89 / 146 与 `tts.say` 暴露全部复现 |

> 诚实标注：「修复前会抖」是**代码事实**（旧分支那一行 `if (exposure == null)` 的直接推论），
> 本次**没有**在旧包上跑一遍抖动的 A/B 来实拍；实拍的是修复后不抖。
>
> 顺带观察到一个**未修**的现象：App 冷启后头几秒 service WebView 尚未就绪，curate 分发拿不到
> 表态——此时「登记了却没表态 ≠ 弃权」的纪律会让该插件的工具本轮不露（实测重启后第一轮
> 「把这段读出来给我听」没露 `tts.say`，warm 之后就正常）。tts 没有 route 钩子兜底，所以冷启
> 那几秒的显式朗读请求会漏。影响短暂、且与本次修复无关，记录备查。

## 修复二：App 冷启的几秒里，好插件可能被永久旁路（2026-07-27）

顺着修复一往下核对时发现的第二个缺陷，**危害比第一个大**（第一个是性能，这个是功能永久失效）。

service WebView 从「创建」到「service.js 加载完」之间有几百毫秒到几秒的窗口。这期间
`evaluateJavascript` 打进去石沉大海（`__ggufDispatch` 还没定义、没人 respond），只能等超时：

1. 白吃整个钩子预算；
2. 被按「超时」记进熔断计数——**而熔断状态落盘**（`_state.json` 的 `bypassed`，本次注错时实测到），
   冷启后连发三条请求就能把一个完全正常的插件**永久旁路**，直到用户手动恢复；
3. curate 面按纪律 3「登记了却没表态」把它的工具藏起来。

第 3 条上纪律 3 的推理**不成立**，而且错法与本轮从桌面端吸收的 `global` 记账反转**是同一种**：
豁免理由是「插件坏了它的 `tool` 钩子同样跑不了」，但没准备好 ≠ 坏了——等模型几秒后真吐标记时
它早就绪、`tool` 钩子跑得动。

**修法**（三处）：`PluginRuntime` 记录就绪位（`onFirstReady` 置位 / `destroyService` 清除）并暴露
`isServiceReady`；`dispatch` 遇未就绪立即返回且**不记熔断**；`AspectRegistry` 把「登记了但未就绪」
归入弃权者（其 callable 照豁免保留），同时把注入位判据换成 `curateRegistered`（静态登记）——
否则冷启那几轮 head 又会抖，等于把修复一的口子从另一侧重新捅开。

**真机验证**：整机冷启后**第一个**被服务的请求（+2.7s）「把这段读出来给我听」→
`curate exposure=tts.say`、`prompt_tokens=146`，工具正常暴露；连发四轮 `bypassed` 始终为 `[]`。
修复前同样流程曾观察到该轮 `exposure=(空)`、朗读工具丢失。

> 诚实标注：冷启窗口在**通常情况下被模型加载时间掩盖**——网关在 llama-server 加载完之前根本
> 不服务请求（实测返回 RemoteDisconnected，此时压根不会分发插件），所以踩中需要「模型已在页
> 缓存、加载极快」这类条件。本次没能按需复现「未就绪跳过」那条日志，因此该路径由**单测**钉死
> （`AspectBusTest` 新增两项），真机侧验证的是「冷启首轮行为正确 + 不被旁路」。

**新增单测**（19 → 21 项）：

- `登记了 curate 但 service 未就绪时 按弃权处理 工具不该被藏起来`
- `教学注入位的判据是登记 不随本轮谁在线变`

## curate 的延迟收益：真机补量（2026-07-27 · ruby 22101316C · MiniCPM5-1B-Q8_0）

v1.1.4 只量了 token（167→17），没量时间。桌面端反哺时指出「延迟才是用户感知，而且能反过来
证伪『判定成本吃掉收益』」，于是补量。**双路测法**：8081 直连 llama-server 做分离计量
（`cache_prompt:false` + `max_tokens:1`，排掉缓存与解码噪声）、8080 网关做真实路径确认。

| 量 | 数值 |
|---|---|
| 全露教学条款（notes.append + tts.say）token 数 | **146**（`/tokenize`） |
| 收窄轮 → 全露轮 prompt | **18 → 169 token** |
| 同上 prefill 耗时（各 3 次中位） | **289ms → 1930ms，省 1641ms**（实测 87.6 t/s ≈ 11.4ms/token） |
| `route`+`curate` 稳态开销 | **≈45ms**（首轮 131ms 含 service WebView 冷启） |
| **净赚比** | **≈ 36 : 1** |
| 真网关三轮 prompt_tokens | 闲聊 **18** / 记录 **89** / 朗读 **146**（v1.1.4 为 17/89/143，稳定复现） |
| 真网关 curate 日志 | `exposure=(空)` / `notes.append` + 动态教学 125 字 / `tts.say` + 202 字 |

**机理（与桌面端不同、方向相同）**：手机的教学在动态位，实测记录轮 `prompt_n=19`、朗读轮
`prompt_n=93`——**教学 token 每轮都要重算**，所以收窄省的是「每轮都省」的 prefill；桌面端教学在
head，是「付一次头部失效换整轮变短」。两条都净赚，幅度与成因不同，故契约只写「必须量」不写幅度。

> 复现脚本（一次性，未入库）：`/tokenize` + `/v1/chat/completions` 直连 8081 各 3 次取中位；
> 网关侧带 `X-GGUF-Session` 走本机路径、`max_tokens` 固定 24。
> **本次测量零改动**：没有改任何插件文件或 manifest（不像 v1.1.4 那次要 `run-as` 摘 curate 钩子）
> ——全露侧是直连 llama-server 用真实教学文本复现的 prompt，属**分离计量**而非端到端 A/B，
> 这点如实标注。测完已把服务停回测前状态（进设备时 llama-server 未运行）。
