## v1.1.15（2026-08-03）—— 插件消息角标支持"条件显示"（requiresCard），修乐句"下载"角标乱挂的问题

反馈：多个插件同时启用后，消息下方动作行的角标会跟着每一条消息一起堆出来，即使这条消息根本用不上——典型例子是乐句插件的"下载"角标，此前只要是 assistant 消息、`roles` 匹配就无条件显示，哪怕这条回复压根不是一段可播放的乐句、没有 .mid 可导出，点了也没有意义。

修法：manifest 的 `messageActions[]` 每一项新增可选字段 `requiresCard`（默认 `false`，向后兼容——已有的朗读角标 `tts.speak` 不用改，任何文字都能读，保持无条件按 `roles` 显示）。声明 `requiresCard: true` 的角标，只有在这条消息的卡片确实由本插件渲染（即 `msg.cardPlugin == 本插件 id`，§6.12 消息卡片机制）时才出现——也就是说，只有真正产出了乐句卡片的那条消息才会挂"下载"角标，普通文字回复不再跟着挂一个用不上的角标。

改动文件：
- `plugin/PluginManifest.kt`：`PluginMessageAction` 新增 `requiresCard: Boolean` 字段；解析处 `a.optBoolean("requiresCard", false)`。
- `ui/ChatScreen.kt`：角标渲染循环里加一道过滤——`if (action.requiresCard && msg.cardPlugin != rec.manifest.id) continue`。
- `assets/plugins/com.gguf.midi/manifest.json`：`midi.download` 声明 `requiresCard: true`，版本号 1.3.3 → 1.3.4（manifest 变更需升版本号才能被宿主识别为升级并释放到设备）。
- `docs/工具插件规范.md`：§2.1 字段说明与校验规则、§6.11 展示条件与典型用途，同步补充 `requiresCard` 的语义与用法建议。

验证：JVM 单测全量跑过（`BuiltinManifestTest` 等 39 项全绿，含所有内置插件 manifest 解析校验）；`assembleDebug`/`assembleRelease` 均编译通过。真机（Redmi ruby，ADB 直接驱动 `input`/`uiautomator dump`/`screencap` 完成测试，非人工操作）：发 "midi" 触发乐句接管，同一助手回合里紧邻卡片的纯文字消息不挂"下载"、卡片本身正常挂"下载"；卡片之后新发的纯文字消息（"Hi"）也不受"会话里出现过卡片"影响，照常不挂——按消息逐条判断，无状态泄漏；`朗读`（`requiresCard` 默认 false）全程不受影响。

## v1.1.14（2026-07-28）—— 外援插件真机验收；修「不接管时没有回落」

上一版（v1.1.13）的日志第九节写了第 12 个内置插件「外援」，结尾标着 ⚠️ 真机未验。这一版把那句话补完：链路在真机上跑通了，同时撞出一个宿主侧的真缺陷。

先把版本账记清楚：外援的代码写于 1.1.13 打包之后（正式包 14:22，插件代码 15:05–15:16），所以 1.1.13 的正式包里其实没有它——它是随这一版第一次出厂的。

**一、接管路径：真机通了**。验收用的"外部端点"是局域网里一台机器上的 OpenAI 兼容假端点（会把收到的请求原样记下来），这样既能看清手机往外发了什么，又不用为验收花钱。这也正是插件推荐的用法之一：端点填家里另一台机器的地址，内容并不出家门。手机上说"帮我写段悲伤的旋律"：乐句接管 → `gguf.llm.chat` → llmRoute 改道 → 外援 service.js → `gguf.net.fetchJson`（宿主代取，绕开 CORS）→ 局域网端点 → 片段回来 → 照常编排成卡片。整轮 1.2s（本机 MiniCPM5-1B 编曲要十几秒），回复是"给你写了一段：Am 小调，76 BPM，悲伤，8 小节 / 0:13，编排 A B A B"，与端点上写死的那段片段一致。端点侧收到的请求证实了四件事：`Authorization: Bearer <key>` 带对了；`temperature: 0.95` / `max_tokens: 300` 照原样透传；`json_schema` 没有透传（按设计——各家云端 API 的结构化输出参数互不相同，硬塞多半 400，调用方本来就有宽容解析兜底）；完整的作曲 system prompt 与用户原话确实离开了手机——这正是 `cap:llm` 被标成高风险的原因。

**二、修「不接管时没有回落」——这次验收唯一的收获**。规范 §6.16 白纸黑字写着：提供者返回 `{}` = 我不接，宿主去打本机模型。没配好、被 `only` 筛掉、超时、HTTP 错、认不出标签，全都走这条。而宿主的 `llmRoute` 只判 `null`。`{}` 在 Kotlin 里是个非 null 的 JSONObject，于是这个空壳被当成答案交给了调用方——调用方多半没有"空壳"这个分支。真机复现：把外援配成"只服务便签"（乐句被筛掉），再说同一句"帮我写段悲伤的旋律"：耗时 0.28s，外部端点收到的请求 0 条（对，它本来就不该接），本机模型压根没被问过，用户看到的是"这次没写出能用的片段，要不换个说法再试试？"。打开一个保底插件，反而把原有能力弄丢了——正是保底最不该有的失败方向，而且它安静得很：没有报错、没有日志、没有熔断，只是能力凭空消失了。修法是把判据从"它有没有回话"改成"它有没有交出这次调用要的东西"：`chat` 看 `content`、`classify` 看 `label`，空壳一律回落本机。这一支不写日志、不记熔断——主动不接是常态（用户只勾了某几个插件走外援），逐轮刷日志没有意义。注意发声（§6.13）的 `{}` 含义正好相反：那边的提供者（变声 / 悠米音色）是自己把声音放完再返回 `{}`，表示"已处理"；这边的提供者只是个中转，不交出内容就等于什么都没发生。同样是空对象，两个能力点的含义相反，所以 `ttsRoute` 保持原样，没有跟着改。

**三、自检**。JVM 单测 31 → 39 项（新增 `LlmProviderRouteTest` 8 项），把这条纪律钉在编译期：空对象 / 只有无关字段 / 空 label / 空 content 都算没接管，给了 content 或 label 才算接管，未知动作向前兼容。理由是这条纪律靠肉眼看不住——`{}` 与 `{content:"…"}` 在类型上毫无区别，代码读起来都对。`node scripts/check-plugins.js`（插件侧 16 条断言）照常全过：插件那一半本来就是对的，返回 `{}` 的方向从一开始就没错，错的是宿主怎么理解它。

**四、真机验收清单**：插件释放到设备（12 个）✅；改道 → fetchJson → 外部端点 → 解析 → 卡片 ✅ 1.2s；key / temperature / max_tokens 透传，json_schema 不透传 ✅ 端点侧逐字核对；被 `only` 筛掉时回落本机模型 ✅（修复后；修复前是这一版的主角）；发声路径不受影响 ✅ ttsRoute 未改动，单测覆盖。

## v1.1.13（2026-07-28）

**乐句能导出成 .mid 了**，外加两个真机撞出来的缺陷。①宿主补第 15 个能力点 `files:save` / `gguf.files.saveDownload`（§6.15）：插件在 WebView 里算得出二进制却没有任何通道交给用户（data: URL 下载在 WebView 里不可靠、storage 只存 JSON），现在经宿主写进系统"下载"（API 29+ 走 MediaStore Downloads，不需要任何运行时权限；8MB 上限、文件名消毒、同名不覆盖）。乐句 1.3.0 据此加消息角标"下载"（与朗读同一行），把乐句编成标准 MIDI（SMF format 1，轨 0 放速度元事件，其余每轨一个 GM 音色）——音符模型本来就是 MIDI 语义（音高 0–127、力度、以 tick 计时长），编码只是写成字节。自检里正经解析写出来的文件：魔数/format/division、note-on 与 note-off 配平且等于音符数、速度元事件与乐句一致、末 tick 等于 totalTicks。②冷启宽限：App 刚起来 service WebView 要几秒才加载完，而用户的第一句话往往紧跟着来，route 拿不到接管、能力就在第一句话上丢了（真机反复撞到）。现在分发前给一次有界等待（最多 2.5s），只等"从没就绪过"的插件——一个插件只可能有一次"从没就绪过"，不是每轮开销。③notice 不再硬套便签的措辞：notice 是所有插件共用的通道（§6.6），旧代码给不以"已/便签"开头的一律加"已记入便签："前缀，于是真机上出现了"已记入便签：这段乐句没认出可用的音符"。④route 判定改两段式：关键字门闸 + LLM 精判（用户的提议，也是 §6.14 早就写下的方向）。手写枚举补不完——这个插件为"写…音乐"栽过三次；一放宽又会把"写个音乐播放器"误接管成作曲。正则吃得下句法、吃不下语义，所以不再指望一条正则同时高召回高精度：高置信说法（作曲/编曲/写段旋律/midi…）快判定直接接管、零成本；拿不准的（句子里有音乐味，但可能在聊音乐、可能要程序）返回 `deep:true` 向宿主申请第二遍，用独立预算（3s，不占 route 的 150ms——那 150ms 是给扫正则的，跟问模型差两个数量级）调一次 `llm.classify` 定夺；都不命中则一分钱不花。真机实测一次判断 Qwen3.5-2B 稳态 1.1s（首次 2.1s），且只落在命中关键字的少数轮次上。fail-open 方向按 route 纪律选：判不出来就不接管（宁可漏，漏了模型自己还能答，误接管是整轮被替换）。宿主侧 `AspectBus.routeUntilTakeOver` 加深判轮 + 4 项纪律单测（已接管就不再深判、没给深判预算则忽略申请、深判预算见底不派、深判带 deep 标记）。顺带修好了 `llm.classify` 在 Qwen 上一直是废的：它把判断指令挂成一条末尾 system，而 Qwen 模板禁止中途 system → 整个判断请求 HTTP 400 → 判断静默失败、调用方只看到"判不出来"（v1.1.12 只修了网关的注入位，classify 是第二条路径，同一个坑又踩一遍）。根因是"模板能力"这个客观事实没共享，现在抽成 `TemplateProbe` 由网关与插件桥共用；模板不吃中途 system 时判断指令改为并进末条用户消息末尾（不新增角色、任何模板都合法，前面消息一字不动）⑤消息卡片展开后收不回去（用户报的）：长按乐句卡片看音符会把下面的"复制/朗读/下载"推下去，再收起时卡片不缩回、留一大块空白。根因在 SDK 的高度回报量的是 `documentElement.scrollHeight`——宿主把 WebView 高度设成上报值之后，它至少等于视口高（被 WebView 自己撑着），于是"内容变矮"永远报不回去，连 ResizeObserver 都不再触发；改成量 body（block 盒，高度随内容缩得回去）并改观察 body⑥route 面预算见底不再静默：curate 面 2026-07-27 已补日志，route 面漏了，而它丢的是"整轮接管"——这次真机定位"乐句插件为什么没接管"为它多花了很久⑦就绪宽限覆盖 WebView 重建：原先只等"从没就绪过"的插件，可 App 切后台再切回来系统会回收 WebView，重建期间的第一句话照样丢接管（真机复现：切回来第一句"write a midi song"没接管、第二句就接管了）；现在重建中的也等，给一半预算

## v1.1.11（2026-07-28）

回答"为什么模型不认识自己的能力"这个反馈，做三件事。①能力清单进首条 system：便签/朗读/乐句各加一句 systemClause（"- 作曲：用户要旋律/曲子/伴奏时直接写给他，别说自己不懂音乐"等，三条合计约 106 字）。它进 head、逐轮字节稳定，所以 KV 前缀命中、只在会话首轮付一次预填——与 curate 收窄不矛盾：curate 省的是"怎么调用"的长教学（逐轮可变、走动态位），这里说的是"你会不会"，必须常在。实测"你能发语音吗"从"作为文本模型我无法发声"变成"当然可以，你希望我发什么内容"。诚实标注：问"你都会做什么"时 1B 仍然背通用助手清单、不读系统提示词里的能力条款（prompt 里确实有），这是模型档位的上限、不是管线问题。②首次分发预热：service.js 加载完即用一个 SDK 不认识的钩子名走一遍完整分发路径（SDK 对未知钩子立即 respond({})，无副作用、不记熔断），把冷启成本从用户的第一句话上挪走——真机 23:35 那轮整条管线花了 480ms，而 route 只有 150ms 预算、乐句插件排在最后一个，直接被预算地板挡掉，能力就在第一句话上丢了。③让"能力静默丢失"可观测："后台脚本尚未就绪"与"本面预算已见底，本轮没轮到它"两类跳过原先只写 logcat（会滚掉，事后无从追查——这次为定位它查了很久），现在进用户可见的运行日志。插件版本：便签 1.0.6 / 朗读 1.1.6 / 乐句 1.2.9

## v1.1.10（2026-07-27）

修乐句插件三处真机撞出来的缺陷（用户反馈"让它创造音乐时，它对自己已有的插件好像没有感觉"）：①音乐意图漏判——用户说"帮我写一个悲伤的调"，而正则只认"曲/旋律/乐句"不认"调"（曲调/调子），于是既没接管也没露工具，模型只能自己发挥去反问"你想要什么风格"；补上 调/调子/谱…曲/伴奏/主旋律/背景音乐/BGM，"调"用否定预查挡掉调用/调整/调试/调查/空调/语调/调休/调色等非音乐义；"使用工具"这类祈使在刚出过乐句的会话里也算续写意图。②情绪夹取被 major 里的 m 骗过——判定小调用的是 `/m|min|小调/`，而"C major"里有个 m，于是被当成"已经是小调"整个跳过，结果"悲伤"配了 C 大调；改成削掉音名后先排除 maj/大调再认 m/min/minor/小调，parseKey 与表头捕获同步收紧（Cmajor 曾被解析成 C 小调），14 种写法双向夹取全部正确。③续写竞态——上一轮的状态只落 storage，紧接着的"使用工具"赶在 storage.set 落地前到达、prev 读成空，于是另起了一首调/速度/情绪全变的新曲子；加同步内存副本（落盘那份留给 WebView 重建后用）。真机复现用户原话：悲伤→Am 小调 76BPM，"使用工具""再来一段"接着长到 23 小节 / 0:36。语料补 15 条真实说法与"调"的非音乐义负例

**GPU/Vulkan 探索**：手机 GPU 为 ARM Mali-G68 MC4，补齐 NDK 缺失的 SPIRV-Headers、Vulkan-Hpp、spirv.hpp 三道 Khronos 头文件依赖后 Vulkan 版 `llama-server` 编译成功，但真机一加载模型即 segfault——根因是 Qwen3.5 系模型用的"Gated Delta Net"线性注意力算子当时 llama.cpp 的 Vulkan 后端不支持，与 Mali 驱动无关。结论：GPU 加速对该模型家族暂不可行，转专注 CPU + 压缩策略。

**19:36** 加入服务器端图片压缩代理（`ImageProxy`）：内置 HTTP 代理拦截请求里的大图，自动解码→缩放→重编码后再转发给 `llama-server`，客户端零改动；过程中挖出隐蔽 bug——Android 默认禁止明文 HTTP，App 没声明 `usesCleartextTraffic`，健康检查请求被系统静默拦截，导致状态永远卡"启动中"、代理也连带没启动；修复为 manifest 加 `usesCleartextTraffic="true"` + 代理进程立即启动。修复后实测：原本 >2.5 分钟超时的 1024px 大图，压缩到 384px 后 84.6 秒完成且答案正确。

**20:58** 把图片最大边长默认值从 384 降到 256（实测 256px 约 29 秒 vs 384px 约 85 秒 vs 原图超时），写入 README 与长期记忆。
