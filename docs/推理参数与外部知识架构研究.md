# MiniCPM5-1B 推理参数与「小模型推理引擎 + 外部知识」架构研究

> 2026-07-18。缘起：此前结论「温度 0 判定最准」，但担心温度 0 自由生成循环；同时想验证设想——
> 把 1B 当纯推理引擎、由检索把世界知识注入上下文，能否以小博大。
> 方法：文献深研（官方结论已三票交叉验证；采样器文献因会话额度中断只过了单轮核验，标注见文末）
> + **Mac M4 Metal + MiniCPM5-1B-Q8_0 本机实测**（脚本在会话 scratchpad `sampler_test.py` / `loop_test2.py`，
> 实验设计与数字全文如下，可复刻）。

## 结论速览

1. **温度 0 循环的恐惧被高估了**：单轮 ≤900 token 自由生成，六个采样档（含纯贪心）全部 0 循环。
   真正的重复问题出在两处：贪心**长生成**的软性重复率升高（0.200 vs 其它档 0.014–0.073），
   以及**多轮对话的跨轮自我模仿**（模型复读自己上一轮的结构/整句）。
2. **repeat_penalty 是判定任务的毒药（本项目最重要新发现）**：`repeat_penalty 1.1` 让 26 条猫名判定
   假阴从 0 → 9（漏掉大多数真相关项）。机制：指令里「只输出 相关 或 不相关」已含「相关」的 token，
   惩罚窗口（默认含 prompt 末 64 token）压低它们，首 token 系统性偏向「不」。
   **受限枚举 + 惩罚类采样器 = 系统性偏置**，且文献证实它对代码也是灾难（HumanEval Pass@1 0.301→0.092）。
3. **DRY 是唯一零副作用的防循环手段**：判定 17/26（与贪心持平、0 假阴）、grounded QA 8/12（持平）、
   长生成重复率砍到 1/3、跨轮复读率 0.22→0.03（六档最低）。默认惩罚窗口=全上下文，恰好覆盖「自己前几轮的话」。
4. **官方从不推荐贪心**：OpenBMB 对 MiniCPM5-1B 的推荐是 think 模式 temp 0.9 / top_p 0.95，
   no-think 模式 temp 0.7 / top_p 0.95（三票验证）。官方只给 temperature+top_p，不给任何防重复参数；
   MiniCPM4-0.5B 的 vLLM 示例用过极轻的 repetition_penalty=1.02。另外 MiniCPM5-1B 的 RL+OPD 训练
   把「跑满 token 预算不停机」的比例压了 29 个百分点——**这代模型在训练侧已治理过循环**，
   与实测「贪心也不硬循环」互相印证。
5. **以小博大：知识可以外置，推理不能外置**。2026 年 scaling-law 研究（arXiv 2604.00715）给了定量答案：
   检索对**知识密集任务**是参数知识的良好替代、小模型受益最大；对**推理密集任务**收益微弱且不稳定。
   实测同样如此：1B 从资料里**取事实**很稳（各档 8–10/12，错的全是算术），**对取出的数字做算术**是重灾区。
   → 架构分工：知识 → 检索外置；推理 → 模型自带 + 任务分解；**算术/比较 → 外包给代码**。

## 一、官方推荐参数（三票交叉验证 ✓）

| 模式 | temperature | top_p | 适用 | 来源 |
|---|---|---|---|---|
| Think（推理/数学/代码/多步） | 0.9 | 0.95 | 开思考时 | HF 模型卡 + GitHub README + llama_cpp.md，3-0 验证 |
| No-think（快速助手，**本项目现状**） | 0.7 | 0.95 | `--reasoning off` | 同上，3-0 验证 |

- 官方文档**只**给 temperature/top_p；repeat_penalty、top_k、min_p 均无官方推荐值。
- 一个被**反驳**的说法：官方推荐 `-c 8192 --jinja` 启动——0-3 验证不通过，别引用。
- MiniCPM5-1B：2026-05-19 发布，标称 131K 上下文（**标称≠有效**，同系 MiniCPM4 预训练 32K + YaRN 外推；
  1B 的有效上下文按小几 K 规划最稳，本项目 memBudget=ctx/8 的做法是对的）。
- think 模式温度更高（0.9）是因为长思维链需要多样性避免思路死循环；本项目关思考，按 no-think 档走。

## 二、循环的真实成因与边界（实测 + 文献）

### 本机实测（M4 Metal, Q8_0；温度外其余参数取 llama.cpp 默认，逐项覆盖）

**T1/T1b 循环倾向**——单轮自由生成 400 token（8 题）与 900 token（5 题，穷举/枚举型诱发题）：

| 档位 | 400t 循环 | 900t 循环 | 900t 平均8字重复率 |
|---|---|---|---|
| 纯贪心 temp 0 | 0/8 | 0/5 | **0.200** ← 软性重复堆积 |
| 贪心 + DRY 0.8 | 0/8 | 0/5 | 0.073 |
| 贪心 + repeat_penalty 1.1 | 0/8 | 0/5 | 0.014 |
| temp 0.6 + min_p 0.05 | 0/8 | — | — |
| temp 0.8（现 app 默认） | 0/8 | 0/5 | 0.025 |

**没有任何一档出现硬循环**（≥10 字片段连续 3 次）。贪心的问题是长生成时软性重复（同一句式、
同一成语反复出现）稳步累积——文献机制：重复片段每复现一次概率被自我强化（Holtzman et al. 2019，
贪心解码 n-gram 重复率 ~43% vs 人类 0.5%；代码研究进一步发现 90% 的重复是「结构重复」而非逐字重复，
且贪心会抑制 EOS——temp 0 时模型跑满 token 预算的比例远高于 temp 0.8）。

**T1b 场景 2：多轮自我模仿（4 轮连问同构问题）——这才是聊天里「循环」的真身**：

| 档位 | 末轮与前三轮的复读率 | 末轮表现 |
|---|---|---|
| 纯贪心 | 0.22 | 正常回答，结构复读前轮 |
| 贪心 + DRY | **0.03** | 正常回答，几乎无复读 |
| 贪心 + repeat_penalty | 1.00 | 掉进「我不能理解你的提问」逐字复读 |
| temp 0.8 默认 | 1.00 | 同样掉进拒答复读 |

跨轮复读是会话级现象：模型把自己前几轮的回答当模板逐字模仿，一旦某轮产出退化句（如拒答），
后续轮贪心地滚进同一吸引子。**DRY 因惩罚窗口默认=全上下文（`dry_penalty_last_n -1`），
恰好把「自己前几轮说过的话」纳入序列匹配，是唯一系统性压制跨轮复读的采样器。**

### 边界

- 循环风险 ≈ 生成长度 × 开放程度 × 会话轮数。**短输出受限解码（判定/抽取）在任何温度下都无循环风险**——
  文献同样支持：贪心的退化专门发生在开放式长文生成，封闭式任务上贪心普遍更优（对 7–8B，
  HumanEval 贪心 58.5 vs 采样 31.8；GSM8K 83.5 vs 72.0），且**模型越小，解码方式对结果的影响越大**。
- 问题求解基准上温度 0–1 内对准确率无统计显著影响（arXiv 2402.05201），封闭式任务最优温度多在 0.1–0.2。
  也有反例：top-nσ（ACL 2025）在推理数据集上超过贪心——「推理必须贪心」不是铁律，但「推理要近贪心」是。

## 三、惩罚类采样器的副作用（重要）

**T3 受限解码判定（26 条猫名集，资料在前排布）**：

| 档位 | 准确率 | 假阳 | 假阴 |
|---|---|---|---|
| 贪心 temp 0 | 17/26 | 9 | **0** |
| 贪心 + repeat_penalty 1.1 | 16/26 | 1 | **9** ← 召回保证崩塌 |
| 贪心 + DRY 0.8 | 17/26 | 9 | **0** |
| temp 0.6 + min_p | 15/26 | 9 | 2 ← 采样噪声也破坏召回 |

repeat_penalty 的毒性机制：枚举答案的 token 已在指令里出现过（「只输出 相关 或 不相关」），
处于惩罚窗口内；输出「相关」首 token 即中招，输出「不相关」首 token「不」无惩罚——
**首 token 被系统性推向「不」**。这与文献对代码任务的结论同构（惩罚合法重复 → 提前终止、语法破坏，
HumanEval Pass@1 从 0.301 掉到 0.092）；DRY 设计文档也明确论证传统惩罚是「钝器」。

**T2 grounded QA（12 题，资料在前，短答案）**——检验「防循环手段会不会误伤照抄资料」：

| 档位 | 准确率 |
|---|---|
| 贪心 | 8/12 |
| 贪心 + repeat_penalty 1.1 | 10/12 |
| 贪心 + DRY 0.8 | 8/12 |
| temp 0.15 + min_p 0.1 | 8/12 |
| temp 0.6 + min_p 0.05 | 8/12 |
| temp 0.8 默认 | 9/12 |

短答案取事实对采样参数**不敏感**（rp 1.1 也没伤到照抄，因为答案短、惩罚累积不起来）。
错题几乎全是算术/状态推理（营收差值算成 1.5、「会议室从 201 换到 505」答成 201、3×10ml 答 10ml、
时刻差算不对）——**是 1B 推理上限，不是采样问题**。

## 四、三档参数建议（直接可落地）

| 参数 | 判定档（L2/工具/抽取） | 推理档（grounded 问答/改写） | 聊天档（自由对话） |
|---|---|---|---|
| temperature | **0** | **0–0.2** | **0.7**（官方 no-think 推荐） |
| top_p | —（受限解码不敏感） | 0.95 | 0.95 |
| min_p | — | 0.05 | 0.05（llama.cpp 默认已有） |
| repeat_penalty | **1.0（严禁 >1）** | **1.0（严禁 >1）** | 1.0（不用它防循环） |
| dry_multiplier | 0（无必要，加了也无害） | 0.8（防长答案软重复，保险带） | **0.8（核心：治跨轮复读）** |
| dry_allowed_length | — | 2（默认） | 2（默认） |
| max_tokens | 给够（防 JSON 外壳截断） | 按需 | 按需 |
| 输出约束 | json_schema 顶层 enum | 尽量 json_schema | 无 |

落地位置（均为**每请求 API 参数**，不动 llama-server 启动参数，互不干扰）：

1. **判定档**：heavymem/linemem 走 `gguf.memllm.chat` 的 L2 判定请求显式带 `temperature: 0`，
   并且**永远不要**给记忆模型实例加全局 `--repeat-penalty`/`--dry-multiplier`（`MemoryModelServer.kt`
   现状只透传 temperature/top_p/max_tokens/json_schema，是安全的——保持这样）。
2. **推理档**：网关里凡「注入了记忆/资料的续写、两段式续段生成、便签操作 Stage2」这类请求，
   按推理档发（现 `runNoteTool` 用 temp 0.2 正确，可补 `dry_multiplier: 0.8`）。
3. **聊天档**：现 app 默认 `--temp 0.8` 建议改 0.7 对齐官方；**真正值得加的是聊天请求体里的
   `dry_multiplier: 0.8`**——这是本次研究对日常体验最有实感的一条改进（治跨轮复读）。
   可在 `ChatViewModel`/网关拼请求时加，不必动启动参数。
4. 判定档的排布沿用已实测结论：`[资料] + [判定任务+问题]`，受限解码 enum（见《记忆检索基准》第三节）。

## 五、「1B 推理引擎 + 外部知识」可行性判断

**判定：方向成立，且是文献正在收敛的共识；但要按「三分工」落地，不能指望检索补推理。**

### 支撑证据

- **检索换参数的汇率**：RETRO 7.5B + 检索库 ≈ GPT-3 175B（语言建模，25× 参数）；Toolformer 6.7B
  借 API 调用超 GPT-3 175B；1–3B + 结构化推理在数学上匹敌 30B+（NVIDIA SLM 立场文引证）。
- **对小模型最划算**（arXiv 2604.00715，2026，OLMo-2 30M–3B 受控实验）：模型越小、
  从检索获益越大；预训练超过 ~4.14 token/参数后，往检索库投数据比继续预训练更划算——
  MiniCPM5-1B（训练远超此比率）正处于「检索红利区」。
- **小库也行**（Retro-li）：检索库不必是千亿 token——57 万 token 的小库就有效，
  且**邻居的语义质量 > 库的大小**（小而准的库胜过大一个数量级的杂库）。
  这正是本项目「会话级记忆 + BM25 粗筛 + L2 精判」的路线。
- **agentic 分工论**（NVIDIA 2506.02153）：任务分解后的子任务足够简单，大模型的广博世界知识
  用不上；受限解码格式输出上，小模型反而比通用大模型更可靠——即本项目「代码路由、模型抽取」
  的既有架构原则。

### 三条分工边界（架构铁律）

1. **知识 → 外置**。事实性内容一律检索注入，实测 1B 照抄资料取事实很稳（各采样档 8–10/12）。
2. **推理 → 模型自带 + 分解**。检索对推理密集任务收益微弱（2604.00715 定量结论：
   "complement, not a universal substitute"）。1B 的推理预算要靠**把任务拆小**来花：
   逐条判定、单步抽取、枚举选择，而不是多步链式推理。
3. **算术/比较/计数 → 外包给代码**。实测重灾区（差值、倍数、时刻差、状态更新全翻车）。
   凡涉及对取出事实的计算，让模型只负责「抽取结构化数字」（json_schema），计算在 JS/Kotlin 里做。
   这与便签系统「两段式 + 代码兜底」的教训一脉相承。

### 关键设计要点

- **噪声是头号风险**：不完美检索可把模型拉到**低于不检索的基线**（Mistral-Large 实证）；
  8B 级模型检索鲁棒性 >80% 的结论**没有 1B 级证据**，只能当外推。对策：召回条数宁少勿多、
  L2 精判当噪声过滤器（现有设计正确）、不确定时宁可不注入。
- **排布再加一条**：开源模型普遍偏好**倒序**——最相关的资料放**最后、紧贴问题**（2505.21870）。
  与本项目「资料在前、任务框架在后」实测兼容，合并为：
  `[次相关资料 … 最相关资料] + [任务框架 + 问题]`。多条注入时按相关度升序排。
- **温度与 RAG 的交互**：答案已在上下文里时用低温（社区共识 0–0.3；实测取事实对温度不敏感，
  低温只赚不亏）——即推理档参数。这也回答了最初的问题：**温度 0 在「外部知识补全」架构里
  不但安全（短输出无循环风险），而且是正确选择；防循环只需在聊天档解决。**
- **上下文预算**：标称 131K 不可当真，注入材料保持精瘦（现 memBudget=ctx/8 合理）；
  KV 前缀缓存约束（字节稳定 head）与低温档天然兼容。

## 七、「按任务自选参数」的形态判断（2026-07-18 定案：底座内置 + 参数导演做插件；未动代码）

> 用户方向：AI 先判断当前任务适合什么参数，再用该参数执行。要求可开关。判断如下，实施等推理引擎升级完成后。

**拆两层，性质不同不共用机制**：

1. **内部定型请求（L2 判定/工具轮/续段）→ 内置，不做开关**。任务类型在代码路径里已定，
   固定参数档是**正确性约束**（rp 毒判定=假阴 0→9），做成可关闭插件 = 用户关掉即静默破坏召回保证。
   落点：各调用点缺省值 + 插件规范红线「判定类请求禁用惩罚采样」。
2. **聊天请求的自适应参数 → 第五个内置插件 `com.gguf.params`（暂名参数导演），默认禁用**。
   聊天是唯一任务类型未知的路径（写诗/算账/代码/闲聊各需不同档）；启发式行为改变理应可回退；
   符合「出厂=裸流式」哲学；settingsCard 放三档数值与分类模式。

**KV 共用判断管线（2026-07-18 用户定案的核心约束：判断与回答共用上文 KV，判断不得污染缓存）**：

> 铁律：**判断请求必须是回答请求同一前缀的严格后缀扩展**。满足则前台模型判断零污染且高速；
> 违反（指令前置/只发用户消息等重排布）则单槽缓存被挤掉、整窗重预填——此前「绝不能用前台模型分类」
> 的判断只针对违反形态，前缀扩展形态反而是**首选模式**。

```
回答请求: [head][历史轮][tail注入][本轮用户消息] + <assistant生成>
判断请求: [同一前缀完全一致] + [判断指令(新system消息)] + 判定档枚举生成1-2 token
```

- 判断：公共前缀全命中，只预填判断指令（~20-40 token）；判定档参数（temp0/无惩罚/json_schema enum）。
- 回答：公共前缀=上文+本轮用户消息（判断时已预填），llama-server `seq_rm` 剪掉判断指令尾巴
  （纯删 KV 不重算——与 1.0.2「重试候选」同机制，真机已验证），预填 assistant 开头即流式。
- 净增延迟：手机 ~1-2s（指令预填+枚举生成；用户消息预填是回答本来要付的），Mac 可忽略。
- 排布巧合：对话在前、判断问题在后 = 实测 69% 的「资料在前」排布，判断准确率天然占优。
- 缓存残留：零——剪尾后下一轮缓存状态与未做判断完全一致。

**管线与分工（修正初版「搭 context 便车」方案）**：判断必须在 context 注入**之后**（前缀须含
head/tail 注入才与回答逐字节一致），且 250ms 的 context 预算装不下 LLM 判断 → 独立 `params` 钩子：
`route → context(250ms) → params(仅插件启用时，预算~4s) → 转发`，插件关闭则该同步点不存在。
机制归宿主、策略归插件（沿用 memllm/host.models 分工）：宿主出桥 `gguf.chat.classify({question,labels})`
（拼前缀+指令、判定档、剪尾、返回标签）；插件在 params 钩子里决定要不要问/标签→参数档映射，
返回 `params` 白名单字段（temperature/top_p/min_p/repeat_penalty/dry_multiplier…），
优先级 = 客户端显式参数 > 插件 params > 启动默认；新权限 `chat:params`。

**分层防线**：JS 规则打头阵（零延迟，明确意图直接命中）；规则拿不准才花 1-2s 走 classify；
外部请求带显式采样参数则整体跳过。memllm 分类降级为备选（冷预填更慢、看不见上文、依赖双模型）。
fail-open 兜底：判断超预算/异常 = 无覆盖 = 现状行为。

**交互注意**：① 插件启用后配置抽屉温度滑杆被每请求覆盖架空，UI 需明示「参数由插件按任务接管」；
② 三档**数值**是 MiniCPM5-1B 实测所得，推理引擎升级若换模型/llama.cpp 版本需重跑 `sampler_test.py`
（机制结论通用，数值不通用）。

**实施顺序（引擎升级完成后）**：网关 params 合并 → 插件 v1 纯规则 → 视需要加 memllm 判定模式。
