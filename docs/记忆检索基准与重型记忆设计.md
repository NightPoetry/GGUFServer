# 记忆检索：速度基准、KV 缓存与排布实验，及「重型记忆插件」设计

> 2026-07-13。缘起：评估把 1B 小模型当「逐条检索器」用（对记忆/语料逐条判相关性）的可行性，
> 以及据此设计一个用**第二个模型在后台做记忆链接与检索**的重型记忆插件。
> 本文的速度/准确率数字都在真机或本机实测得来，脚本见 `/Volumes/UserData/Projects/LLM/_order_test*.py`。

## 一、速度基准（MiniCPM5-1B-Q8_0）

| 指标 | Mac（Apple M4, Metal, `llama-bench`） | 手机（Redmi ruby, CPU） | 倍数 |
|---|---|---|---|
| Prefill / 吃 prompt | **~2000 tok/s** | ~27 tok/s | ~74× |
| 生成 | **~91 tok/s** | ~10.6 tok/s | ~8.6× |

逐条检索的成本主要在 **prefill 每条资料 + 生成一两个 token 的判定**。

- **Mac 完全撑得住逐条检索**：固定指令走缓存后，每条 ~100 token 的资料 ≈ 80ms（~12 条/秒），
  ~300 token ≈ 180ms（~5–6 条/秒）；再加 llama-server 并行槽批处理还能更高。200 条 × 200 token
  硬扫也就 ~20 秒。
- **手机勉强**（prefill 27 tok/s）：逐条 LLM 判定很慢，更适合「BM25 粗筛 → 只让 1B 精判 top-N」。

## 二、检索场景下的 KV 缓存

**缓存能省的是「多次调用之间不变的那段前缀」，不是「每条新资料」**——新资料是新内容，总得 prefill 一次。
决定缓存收益的是「谁不变」，不是「谁更长」：把跨调用不变的一侧放前面。

- **固定一份资料、反复问不同问题**：`[资料(固定)] + [问题(变)]` → 资料只 prefill 一次，之后每问只 prefill 问题。
  实测同段 2000-token 资料问 50 个问题：不缓存 ~50s，缓存资料 ~1.5s。
- **一个查询扫很多不同资料（真·逐条检索）**：变的是资料 → 只能查询在前、资料在后，缓存查询；
  但每条资料只出现一次、无从复用，缓存基本帮不上忙（好在 M4 prefill 快，硬扫也够快）。
- 真值实测：本项目手机端同会话第二条请求 `cached_tokens = 407/408`，前缀几乎全命中——**MiniCPM5 是标准
  因果注意力，KV 前缀缓存正常**（会破坏它的是线性/混合注意力等新架构，如 Qwen3.x 的 Gated Delta Net，
  跟「新老模型」的直觉相反）。
- 极致复用同一套资料：`--slot-save-path` + `/slots/{id}?action=save|restore` 可把 prefill 好的资料 KV 存盘、
  每次查询前 restore，跨请求甚至跨重启不再重算；代价是每种排布/每份资料各存一份，且受「资料在前」约束。

## 三、排布实验：资料在前 vs 指令在前（结论出人意料，已实测纠错）

**任务**：判断一条资料能否回答「用户养的宠物猫叫什么名字」。26 条含陷阱（提了猫但没名字→不相关、
有别的宠物名但不是猫→不相关）。MiniCPM5-1B，受限解码（顶层 enum `相关/不相关`），温度 0。

| 排布 | 准确率 | 假阳(误判相关) | 假阴(漏判) |
|---|---|---|---|
| ① 指令+问题**在前**，资料在后 | 12/26 = **46%** | 14 | 0 |
| ② 资料**在前**，指令+问题在后 | 18/26 = **69%** | 8 | 0 |
| ③ 指令在前、问题紧贴生成点 | 12/26 = **46%** | 14 | 0 |

**曾经的直觉是错的**：原以为「指令在前，模型带着问题读资料判得更准」；实测**资料在前反而更准（69% vs 46%）**。
三向对照（③）证明驱动因素**不是「问题离生成点远近」**，而是——

> **判断任务的框架句要放在资料之后**：先给材料、再问「这能回答 XX 吗」，比先说「判断能否回答 XX」再喂材料好。
> 原因：任务框架前置时，1B 带着「我要找相关」的预期去读满是关键词的材料，退化成关键词匹配、一律「相关」；
> 框架后置时它读完材料才被问，判得更冷静。

**两个重要副结论**：
1. **三种排布都 0 假阴**——从不漏掉真正相关的。所以当**召回优先的粗筛器**用没问题（不丢相关项），
   「资料在前」只是多砍假阳、更干净。当高精度精筛则 69% 仍一般。
2. **对缓存的含义也反了**：对「固定资料反复问」，资料在前**既能缓存资料又判得更准**，没有质量-速度取舍
   （与最初判断相反）。只有「一个查询扫很多不同资料」时才有轻微张力（想缓存查询需查询前置，而查询前置更不准）。

**边界**：这是 MiniCPM5-1B + 这个具体任务的结论，方向未必对所有模型/任务成立。**教训是「别拍脑袋，测一下」。**
落地检索器时按此排布：`[这一条资料] + [判定任务 + 查询]`，输出用受限解码锁成枚举，max_tokens 给够（别被 JSON 外壳截断）。

## 四、「重型记忆插件」设计（双模型 · 后台检索 · 默认关闭）

目标：问问题时，**后台用一个专门的记忆模型**（如 MiniCPM5-1B）对历史/记忆做 LLM 级的链接与逐条检索，
把相关记忆注入上下文，**且不拖慢前台回复**。与现有两个记忆插件的定位：

| 插件 | 检索方式 | 成本 |
|---|---|---|
| `com.gguf.memory` | BM25 词法检索 | 极低，纯 JS |
| `com.gguf.linemem` | 闲置时滚动摘要 + 长期事实抽取 | 中，复用前台模型闲置时段 |
| **`com.gguf.heavymem`（新）** | **第二个模型后台 LLM 逐条检索/链接** | **高，需双模型加载 → 默认关闭、opt-in** |

关键设计点（待与需求方对齐，见文末）：
1. **双模型加载**：宿主再拉起一个 llama-server 实例（内部端口 +2）加载「记忆模型」；插件经新桥接口
   `gguf.llm.chat({model:"memory", …})` 路由到它。RAM：前台模型 + MiniCPM5-1B(~1.2GB) + App，手机 11GB
   下小前台模型可行、大前台模型吃紧 → 故默认关闭并在启用时红字提示。
2. **「不影响前台输出」的真相与时机**：手机是 **CPU-only**，两个模型并发会**互抢 CPU 核**——纯并发反而拖慢前台。
   三种可选时机（见文末决策）：**(A) 一轮延迟**（检索结果注入下一轮，前台零延迟、记忆滞后一轮）；
   **(B) 前置阻塞**（回复前等检索完再注入本轮，本轮即用、起步稍晚）；
   **(C) 闲置预取**（像 linemem 一样只在闲置时用记忆模型预先把记忆链接/索引好，提问时直接查已整理结果，
   提问瞬间不现调大模型）。
3. **检索排布用第三节的结论**：`[记忆条目] + [当前问题 + 判定任务]`，受限解码枚举，KV 缓存固定前缀。
4. **自己的设置卡片**：在设置页有一张卡片，用来选「记忆模型文件」、时机策略、每轮召回条数等（见第五节）。

## 五、插件设置卡片能力（插件系统扩展）

给插件系统新增「设置页 UI 卡片」：启用的插件可在**设置页**渲染一张属于自己的卡片（区别于交互门户的面板），
用于放常驻配置（如重型记忆插件选记忆模型）。推荐实现（与现有 WebView 架构一致）：

- manifest 新增可选字段 `settingsCard: "settings.html"`（或复用 `entry`）声明设置卡片入口；
- 设置页为每个「已启用且声明了设置卡片」的插件渲染一个 `WebView`，加载该 html，复用 `PluginRuntime`
  的面板 WebView 基础设施与 `window.gguf` 桥（storage/llm/host 等）；卡片高度自适应内容。
- 卡片内用 `gguf.storage` 存配置、`gguf.host` 读机型信息；选模型文件等需要宿主给一个「列出可用 GGUF」的
  只读桥接口（新增 `gguf.host.models()` 之类）。

> 备选：manifest 声明式字段（host 渲原生 Compose 控件）——更安全但表达力弱。本项目既有栈是 WebView，
> 故推荐 WebView 卡片以保持一致。

## 六、把 GrowBox 记忆置换系统「翻译」到手机插件尺度

> 用户要求重型记忆插件遵循 `Helper/GrowBox_DeepseekV4ByV4AndOpus` 的设计原理（记忆置换系统 = 虚拟内存分页）。
> **GrowBox 是整套 Rust 系统（redb 磁盘 / ANN 向量 / 指针图 / 做梦周期），手机 WebView 插件只能移植其原理、不可能照搬。**
> 下表是「原理 → 手机插件版」的落地映射（保留铁律，简化实现）。

| GrowBox 概念 | 手机重型记忆插件版（com.gguf.heavymem） |
|---|---|
| **存放区**（唯一临时记忆，两态铁律：在/移除、原位不动、字节稳定 → 保 KV 前缀缓存） | **context 钩子注入的 head 记忆块**——正是 linemem 已验证的「字节稳定 head → KV 缓存」做法。存放区内容只有「在/移除」两态，不随热度重排 |
| **冷归档**（redb 无界磁盘） | `gguf.storage` KV（每条记忆一条目）+ 会话历史（ChatStore）；受 5MB KV 上限约束，超限落更粗的摘要 |
| **索引区**（RAG 向量 + L2 LLM 读原文，殊途同归调入同一存放区） | **双索引手段**：① BM25 词法（现成、快，RAG-analog，「假指针」不留序列锚）；② **L2 = 记忆模型读原文判相关/建链**（用第三节「资料在前」排布 + 受限解码） |
| **指针网**（一次/二次指针，被索引即沉淀，越用越快） | 记忆条目间的**关联边** `node→node`（存 KV 的邻接表）；每次索引命中都沉淀一条边（原则2：扫描副产品全沉淀） |
| **三级缓存**（热指针 LFU，在 RAM 不在上下文） | 热度计数（LFU/LRU）决定哪些条目**进存放区**；纯元数据、不进上下文 |
| **做梦 / 碎片整理**（扫未扫中段还债、二次指针升一次、发散思考建联想） | **闲置时**记忆模型：沿边**发散联想**扩展、给未索引的记忆建关联边、把临时二次边固化为一次边——= 用户说的「闲置碎片整理 + 发散思考预建索引」 |
| **置换 page in/out** | 存放区满 → 按热度淘汰（移除，触发一次前缀重建）；miss → 沿边/BM25/L2 召回调入 |

**双模型宿主支持**（宿主新增）：`LlamaServerService` 再 `ProcessBuilder` 拉一个 llama-server（内部端口 +2）加载「记忆模型」，
只绑 127.0.0.1；桥 `gguf.llm.chat({model:"memory", …})` 路由到 +2。默认关闭；手机 RAM 紧，启用时红字提示（前台+记忆模型双份显存/内存）。

**两段式回复（"先回复→回忆中→再输出"，不影响前台）**——这是最难的、要扩网关协议的一块：
1. 前台模型**立即流式应答**（"让我想想关于 X…"），前台零等待；
2. 插件后台用**记忆模型**做检索/发散（闲置已预建索引 → 提问时多为快速查表 + 少量 L2 确认）；
3. 出**「回忆中」**提示（走现有 notice / SSE 扩展字段通道）；
4. 检索完 → 网关**追加一段续写**：以召回的记忆为上下文，让前台模型再生成一段接在后面（= 第二次生成，作为同一条回复的续段）。
   > v1 可先退化为**一轮延迟**（本轮只做①②③把记忆备好，注入**下一轮** head），把「续写」协议留到 v2——功能等价、协议简单、也完全「不影响前台」。

   不延迟），若有 continuation 插件 → `emitNoticeChunk` 发「正在回忆…」→ dispatch `continuation`（预算 90s，fail-open）→ `emitSyntheticContent`

   关掉即回退纯一轮延迟。**真机端到端 SSE 验证通过**：流式请求 → ① 前台先答（无记忆时甚至猜错名字）② 「正在回忆…」通知
   ③ 续段「对了，我记得我家那只猫叫唐元，小白猫，蓝色眼睛」——召回真记忆、前台模型自然纠正补充。
   踩坑修复：(a) 网关 continuation payload 要**扁平**（turn 字段平铺+content），否则钩子 `turn.text` 取不到→query 空→直接 return；
   (b) 续段候选**用纯 BM25**（不碰记忆模型）避免与闲置 worker 建边抢占单槽→续段稳定触发；(c) genContinuation 前台 1B 偶尔不肯生成→
   **兜底直接陈述召回记忆**，保证「回忆中」后必有产出。

## 待对齐/已定的决策

- ✅ **记忆作用域 = 会话级（2026-07-14 用户定案「保留会话级别即可」）**：heavymem 与 linemem 都按 `hm:<sessionId>`/
  `mem:<sessionId>` **每会话独立**，只读当前会话历史（权限 `chat:read`，无 `sessions:read`）。**这是有意为之、与 GrowBox
  「记忆无界·全局」原理刻意不同**——换对话即全新记忆、互不渗透。别当缺陷去改成全局。若将来要全局：加 `sessions:read` +
  全局键 + 扫全部会话，另议。


- ✅ **检索时机**：闲置预取 + 提问时两段式（v1 先做「闲置预取 + 一轮延迟」，续写协议留 v2）。
- ✅ **先做哪块**：全都要，按上面 1→2→3→4 的依赖顺序推进。
- ✅ **GrowBox 保真度（2026-07-13 用户定案「核心染色和碎片原理相同即可」）**：按「保留铁律、简化实现」原理移植；
  **redb/ANN/完整指针生命周期不照搬**，但**染色（scan coverage 覆盖标记）与碎片（跳过未扫中段=欠债）两套机制的核心原理必须一致**——
  阶段 3 重型插件的硬要求：
  - **碎片**：L2/记忆模型沿指针/锚跳到目标时，被跳过的「未扫中段」记为碎片欠债；
  - **染色**：给记忆序列标记扫描覆盖（已扫=深、锚跨未扫=浅），据此定位碎片、并让后续扫描**跳过已染色区加速**；
  - **做梦（闲置）**：扫碎片还债 + 二次锚升一次指针（覆盖连续后消除碎片）。
  这套「越用越快 + 闲置补债」的飞轮是保真重点，其余（磁盘引擎、向量 ANN、假指针物化对象）按平台简化。
