# 正式包版本历史

每个版本号后跟该版本主要升级备注（打包时由 scripts/release.sh 自动追加）。

- **v1.1.7**（2026-07-27）— route 接管判定收紧——把 curate 那套「带标注语料 + 指标」的方法用到 route 上，实测**误接管率 31%**（4/13）。四条误接管全是「在**谈论**便签这个功能」被当成「在**操作**它」：原判定只要求「句子里有『便签』」∧「句子里有编辑动词」，两者可以隔着十万八千里，于是「便签这个功能怎么用？我想改一下我的工作流」「帮我把这段代码改一下，顺便讲讲便签原理」「你觉得便签和备忘录哪个好用？我在考虑换成印象笔记」「便签的数据存在哪里？误删了能恢复吗」都会被整轮劫持进编辑流程——而那个流程会去改用户真实的便签。route 与 curate 的代价方向相反（curate 判错只多花点 token，route 判错是整轮被替换），所以这里 precision 第一、宁可漏接管。收紧办法不是加否定词表（列不完），而是要求**动词与便签在句法上真的挨着**：调参集与**未参与调参的泛化集**双双 precision 100% / recall 100%。顺带记下一条经验：**句法判定能靠正则、语义判定不能**——同一套方法下 route 泛化集 100%，curate 泛化集只有 42%，判定形态决定了正则的天花板。便签 1.0.4；check-plugins.js 增 route 语料 22 条（含零误接管硬门）+ 泛化集 13 条
- **v1.1.6**（2026-07-27）— 两块。①**定向审计修 5 个失败路径缺陷**——按 v1.1.5 那两个缺陷的病型（逐轮可变的运行结果影响本应字节稳定的东西 / 瞬时失败被记成持久惩罚 / 能力静默丢失）成建制找了一遍，5 条全部核实成立并修复：context 插件本轮超时会让它的 head 整段消失、首条 system 字节随之抖动（现改为复用它上一轮成功的 head，模型也不会凭空少掉人设或长期记忆）；串行面共享预算无下限，排在后面的插件拿到十几毫秒必然超时、而超时记进熔断账本连续三次就永久旁路且落盘（现加 MIN_VIABLE_BUDGET_MS=40，预算见底就根本不派——被饿死不是它坏了）；承上，被饿死的 curate 处理器原按「登记了却没表态」藏掉它的工具，现区分「派了但它自己坏了」与「压根没派到」，后者按弃权豁免；GATEWAY_HOOKS 漏了 curate，只登记 curate 的插件会被判成不是中间件、走零插件快路径而永不分发；reconcile 与 destroyService 的 TOCTOU 会留下「已启用却没有 service WebView」的终态、此后 dispatch 静默返回 null 且不记任何错。单测 21→24 项。②**curate 快判定按标注语料重做**
- **v1.1.5**（2026-07-27）— 修两个 KV/熔断层面的真缺陷（都由「桌面端切面反哺评估」核对纪律时撞见，不是新功能）：①教学注入位曾用「本轮 exposure 是否为 null」判定，而 null 有两种成因——「无人登记 curate」（静态）与「登记了但全员异常/超时」（逐轮可变的运行结果），后者会让首条 system 的字节随 curate 的成败逐轮抖动（违反红线 5「head 必须字节稳定」），抖动那轮连同抖回去的下一轮各重算一次整段 prefill（实测 169 token ≈ 1.9s）；判据改为「有没有插件登记 curate」，失败轮退化成「在动态位全露」，head 恒定、历史 KV 不受牵连。②App 冷启时 service WebView 有几百毫秒到几秒未就绪，此间 dispatch 石沉大海只能等超时，既白吃满钩子预算又被按「超时」记进熔断计数——而熔断状态是落盘的，冷启后连发三条请求就能把一个好插件永久旁路；现在 dispatch 遇未就绪立即返回且不记熔断，curate 面把「登记了但未就绪」按弃权处理（「没准备好」≠「坏了」：等模型几秒后吐标记时它早就绪、tool 钩子跑得动，不该藏它的工具）。另：真机补量 curate 收窄的延迟收益（省 1641ms prefill vs 45ms 判定成本，净赚约 36:1）；规范 §13.7 新增「跨宿主契约：哪些是不变量、哪些是宿主绑定」，吸收桌面端「小模型轮椅」反哺的 scope/governs 辖域契约（含 own/global 记账相反这一条关键坑）。单测 19→21 项
- **v1.1.4**（2026-07-25）— curate 切面真正开始收窄（阶段 3.5）——便签/朗读各自登记 curate 处理器，用正则级快判定决定「本轮该不该把自己的工具露给模型」，闲聊轮不再注入工具教学（省 1B 极其金贵的 system 预算）；SDK 补上 gguf.hooks.curate（阶段 3 只做了宿主侧，JS 侧一直 undefined、插件根本注册不上）；内核补两条纪律——弃权豁免（没登记 curate 的插件的 callable 不因别人收窄而消失）+ 动态注入位（有人表态时教学条款从首条 system 改插到末条用户消息之前，否则每次意图切换整条 prompt 前缀作废、手机上要重算整段 prefill）；fail-open 升为 AspectBus 自带属性（处理器抛错一律当无返回，CancellationException 原样上抛）；heavymem 1.0.6 召回块按相关度升序（最相关贴指令）+ 计算类问答改「模型只抽数字(json_schema)、加减乘除交 JS」两段式；新增 19 项 JVM 单测（AspectBus 分发纪律/curate 语义 + ToolTagScanner 流式零泄漏，正是真机验收里两条 ⚠️ 覆盖不到的路径）与 node scripts/check-plugins.js 插件离线自检。设计见规范 §6.14/§13.4
- **v1.1.3**（2026-07-21）— 插件系统演进为「切面微内核」阶段1-3（等价重构·行为不变·真机验收通过）——内核唯一原语=在一小组具名切面上注册处理器并按预算/权限/熔断/fail-open分发（注册面 callable/ui/capability·管线面 route/curate/context/params/generate/stream/after·分发面 dispatch）；新增 AspectBus 内核（Aspects 切面常量+每切面预算 / AspectRegistry 启用插件→管线面投影 / routeUntilTakeOver·parallel·serialForEach 分发组合子），把 Gateway 固定流水线改为按管线面顺序 dispatch；工具系统收敛为内置 type:tool 运行时插件（CapabilityRuntime 接口 + Runtimes 注册表 + ToolRuntime，"加一种能力类型=加一个 runtime、内核不动"由此为真）；新增 curate 切面（按需给小模型露 callable，无处理器则 exposure=null 全露、逐字节等价 v1）+ generate 显式化（takeOver=替换默认 generate）；现有 manifest 字段/钩子名/桥接口/真机行为全不变，KV 前缀缓存字节稳定（真机 prompt_n 28→1）。设计见规范 §13，迁移与真机结果见 docs/切面微内核迁移进展.md
