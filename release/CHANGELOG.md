# 正式包版本历史

每个版本号后跟该版本主要升级备注（打包时由 scripts/release.sh 自动追加）。

- **v1.1.13**（2026-07-28）— **乐句能导出成 .mid 了**，外加两个真机撞出来的缺陷。①宿主补第 15 个能力点 `files:save` / `gguf.files.saveDownload`（§6.15）：插件在 WebView 里算得出二进制却没有任何通道交给用户（data: URL 下载在 WebView 里不可靠、storage 只存 JSON），现在经宿主写进系统「下载」（API 29+ 走 MediaStore Downloads，不需要任何运行时权限；8MB 上限、文件名消毒、同名不覆盖）。乐句 1.3.0 据此加消息角标「下载」（与朗读同一行），把乐句编成标准 MIDI（SMF format 1，轨 0 放速度元事件，其余每轨一个 GM 音色）——音符模型本来就是 MIDI 语义（音高 0–127、力度、以 tick 计时长），编码只是写成字节。自检里正经解析写出来的文件：魔数/format/division、note-on 与 note-off 配平且等于音符数、速度元事件与乐句一致、末 tick 等于 totalTicks。②**冷启宽限**：App 刚起来 service WebView 要几秒才加载完，而用户的第一句话往往紧跟着来，route 拿不到接管、能力就在第一句话上丢了（真机反复撞到）。现在分发前给一次有界等待（最多 2.5s），只等「从没就绪过」的插件——一个插件只可能有一次「从没就绪过」，不是每轮开销。③**notice 不再硬套便签的措辞**：notice 是所有插件共用的通道（§6.6），旧代码给不以「已/便签」开头的一律加「已记入便签：」前缀，于是真机上出现了「已记入便签：这段乐句没认出可用的音符」。④**route 判定改两段式：关键字门闸 + LLM 精判**（用户的提议，也是 §6.14 早就写下的方向）。手写枚举补不完——这个插件为「写…音乐」栽过三次；一放宽又会把「写个音乐播放器」误接管成作曲。正则吃得下句法、吃不下语义，所以不再指望一条正则同时高召回高精度：**高置信说法**（作曲/编曲/写段旋律/midi…）快判定直接接管、零成本；**拿不准的**（句子里有音乐味，但可能在聊音乐、可能要程序）返回 `deep:true` 向宿主申请第二遍，用独立预算（3s，不占 route 的 150ms——那 150ms 是给扫正则的，跟问模型差两个数量级）调一次 `llm.classify` 定夺；都不命中则一分钱不花。真机实测一次判断 Qwen3.5-2B 稳态 1.1s（首次 2.1s），且只落在命中关键字的少数轮次上。fail-open 方向按 route 纪律选：判不出来就不接管（宁可漏，漏了模型自己还能答，误接管是整轮被替换）。宿主侧 `AspectBus.routeUntilTakeOver` 加深判轮 + 4 项纪律单测（已接管就不再深判、没给深判预算则忽略申请、深判预算见底不派、深判带 deep 标记）。**顺带修好了 `llm.classify` 在 Qwen 上一直是废的**：它把判断指令挂成一条末尾 system，而 Qwen 模板禁止中途 system → 整个判断请求 HTTP 400 → 判断静默失败、调用方只看到「判不出来」（v1.1.12 只修了网关的注入位，classify 是第二条路径，同一个坑又踩一遍）。根因是「模板能力」这个客观事实没共享，现在抽成 `TemplateProbe` 由网关与插件桥共用；模板不吃中途 system 时判断指令改为并进末条用户消息末尾（不新增角色、任何模板都合法，前面消息一字不动）⑤**消息卡片展开后收不回去**（用户报的）：长按乐句卡片看音符会把下面的「复制/朗读/下载」推下去，再收起时卡片不缩回、留一大块空白。根因在 SDK 的高度回报量的是 `documentElement.scrollHeight`——宿主把 WebView 高度设成上报值之后，它至少等于视口高（被 WebView 重建**：原先只等「从没就绪过」的插件，可 App 切后台再切回来系统会回收 WebView，重建期间的第一句话照样丢接管（真机复现：切回来第一句「write a midi song」没接管、第二句就接管了）；现在重建中的也等，给一半预算
- **v1.1.12**（2026-07-28）— **chat 模板随模型走，宿主自动适配**。换 Qwen3.5-2B 一试就炸：凡是 curate 露了工具或 context 注入了 tail 的轮次**整轮 HTTP 400**——Qwen 的模板显式 raise_exception("System message must be at the beginning.")，而 v1.1.4 为保 KV 前缀把逐轮可变内容放在「末条用户消息之前的一条独立 system」，MiniCPM 的 chatml 吃得下、Qwen 不吃。这不是能 fail-open 掉的小事，是整轮报错。现在宿主用 llama-server 的 /apply-template 在**每个模型首次使用时探两件事**（按 alias 缓存，换模型自然重探）：①首条 system 支不支持 ②中途 system 支不支持；据此选注入位——中途 system 不支持就把逐轮内容并进末条用户消息开头（位置一样靠后，**KV 前缀同样不受影响**，这本就是当初挪位置的目的），首条 system 都不支持（Gemma 系）就把所有系统内容并进首条用户消息。探测结论写进运行日志。真机：Qwen3.5-2B 上 400 全消（「你能发语音吗」「读一下这句话」prompt=210/212 正常），日志显示「首条 system=支持，中途 system=不支持」。**顺带回答了「为什么模型不认识自己的能力」**：v1.1.11 加的能力条款在 1B 上被无视（它背通用助手清单），换 2B 后它把三条能力原样列出，还**自己吐出了 <tool name="tts.say"> / <tool name="notes.append"> 标签**——工具协议在 2B 上是通的，1B 从来不行。所以那是模型档位的上限，不是管线问题，现在有对照实证
- **v1.1.11**（2026-07-28）— 回答「为什么模型不认识自己的能力」这个反馈，做三件事。①**能力清单进首条 system**：便签/朗读/乐句各加一句 systemClause（「- 作曲：用户要旋律/曲子/伴奏时直接写给他，别说自己不懂音乐」等，三条合计约 106 字）。它进 head、逐轮字节稳定，所以 KV 前缀命中、只在会话首轮付一次预填——与 curate 收窄不矛盾：curate 省的是「怎么调用」的长教学（逐轮可变、走动态位），这里说的是「你会不会」，必须常在。实测「你能发语音吗」从「作为文本模型我无法发声」变成「当然可以，你希望我发什么内容」。**诚实标注**：问「你都会做什么」时 1B 仍然背通用助手清单、不读系统提示词里的能力条款（prompt 里确实有），这是模型档位的上限、不是管线问题。②**首次分发预热**：service.js 加载完即用一个 SDK 不认识的钩子名走一遍完整分发路径（SDK 对未知钩子立即 respond({})，无副作用、不记熔断），把冷启成本从用户的第一句话上挪走——真机 23:35 那轮整条管线花了 480ms，而 route 只有 150ms 预算、乐句插件排在最后一个，直接被预算地板挡掉，能力就在第一句话上丢了。③**让「能力静默丢失」可观测**：「后台脚本尚未就绪」与「本面预算已见底，本轮没轮到它」两类跳过原先只写 logcat（会滚掉，事后无从追查——这次为定位它查了很久），现在进用户可见的运行日志。插件版本：便签 1.0.6 / 朗读 1.1.6 / 乐句 1.2.9
- **v1.1.10**（2026-07-27）— 修乐句插件三处真机撞出来的缺陷（用户反馈「让它创造音乐时，它对自己已有的插件好像没有感觉」）：①**音乐意图漏判**——用户说「帮我写一个悲伤的调」，而正则只认「曲/旋律/乐句」不认「调」（曲调/调子），于是既没接管也没露工具，模型只能自己发挥去反问「你想要什么风格」；补上 调/调子/谱…曲/伴奏/主旋律/背景音乐/BGM，「调」用否定预查挡掉调用/调整/调试/调查/空调/语调/调休/调色等非音乐义；「使用工具」这类祈使在**刚出过乐句的会话**里也算续写意图。②**情绪夹取被 major 里的 m 骗过**——判定小调用的是 /m|min|小调/，而「C major」里有个 m，于是被当成「已经是小调」整个跳过，结果「悲伤」配了 C 大调；改成削掉音名后先排除 maj/大调再认 m/min/minor/小调，parseKey 与表头捕获同步收紧（Cmajor 曾被解析成 C 小调），14 种写法双向夹取全部正确。③**续写竞态**——上一轮的状态只落 storage，紧接着的「使用工具」赶在 storage.set 落地前到达、prev 读成空，于是另起了一首调/速度/情绪全变的新曲子；加同步内存副本（落盘那份留给 WebView 重建后用）。真机复现用户原话：悲伤→Am 小调 76BPM，「使用工具」「再来一段」接着长到 23 小节 / 0:36。语料补 15 条真实说法与「调」的非音乐义负例
- **v1.1.9**（2026-07-27）— 新增第 11 个内置插件「乐句」（com.gguf.midi 1.2.2）——让模型作曲，端上合成播放，一条可播放的乐句卡片。设计沿用本项目「以小博大」的路子：模型只出创意里最小的那一点（一个 4 小节片段 + 一行播放顺序），确定性的活全交给 JS（宽容解析音名/简谱、按调式自动配低音与和声、三轨音域折叠、多乐器音色、逐轨混音 + 软限幅、钢琴卷帘、Web Audio 滚动预排）。**情绪可点菜**：说「悲伤/欢快/安静/紧张…」时，调式速度音色由插件按乐理查表定并把模型矛盾的取值夹回去（模型给「悲伤 + 140BPM 大调」会被改成小调 76BPM）——这类常识属于该外置给代码的部分。**长曲子靠多轮续写而不是机械重复**：说「再来一段」时沿用同调同速同音色（风格统一）、只让模型写一个新片段（富有变化），JS 接到已有编排后面并回一次主题；真机实测 10→20→32 小节。续写的接管门是「本会话刚出过乐句」的同步标记（按会话记）——否则「再来一段」在写文章的语境里会被劫持整轮。模型交白卷时用主题做确定性变奏（移调/逆行轮换）接上并如实说明。真机验证：卡片渲染与语音卡片同构（点按播放/长按看音符）、声音已由用户耳朵确认、curate 只在要音乐时露工具、别的会话说「再来一段」不被劫持。另新增 BuiltinManifestTest：内置插件 manifest 过不了校验时会「改了却静默不释放到设备」（本次真踩到），现在编译期就能发现
- **v1.1.8**（2026-07-27）— params 任务分档修一个「顺序按直觉排」造成的最坏方向误判。三档 precise(0温)/creative(0.9温)/chat(0.7兜底) 的误判代价不对称：precise 型跑进 0.9 温度最严重（拿 0.9 的温度生成代码、算算术），creative 型跑进 0 温度只是干瘪，判不出来落 0.7 中间档最轻。而 ruleClassify 原本 creative 先判、precise 后判，两张关键词表都命中时谁在前谁赢 ⇒「写个函数生成随机诗句」「写个脚本把歌词按行分割」「帮我写段代码，给这些故事排个序」统统进 0.9 温度，正好是最坏的一种。改成 precise 优先（冲突时偏精确档：把诗写干一点远好过把代码写错），并补齐算术同义说法（「1+2 等于几」「算算我这个月一共花了多少钱」「15% 的税要交多少」原先都落 0.7 档而算术在 0.7 下会算错）。调参集 29/29、未参与调参的留出集零严重误判（留出集还抓到我为补算术放宽正则时的自伤：「我打算下个月搬家」「我们一共聊了挺久」被判进 0 温度，已收回）。另实测了插件自带的 LLM 判断路径（默认关）：规则漏掉的 7 条里判对 6 条、零严重误判，但每次判断 1150-1288ms，而「规则拿不准」本就包含所有普通闲聊 ⇒ 打开后每句闲聊多等 1.2s。结论是默认关正确、不改；但设置卡原文写「额外耗时约等于预填几十 token」低估了一个数量级（成本在解码标签不在预填），已按实测重写，让这个开关变成知情选择。params 插件 1.0.2；check-plugins.js 增 params 语料 29 条（含零严重误判硬门）+ 泛化集 16 条
- **v1.1.7**（2026-07-27）— route 接管判定收紧——把 curate 那套「带标注语料 + 指标」的方法用到 route 上，实测**误接管率 31%**（4/13）。四条误接管全是「在**谈论**便签这个功能」被当成「在**操作**它」：原判定只要求「句子里有『便签』」∧「句子里有编辑动词」，两者可以隔着十万八千里，于是「便签这个功能怎么用？我想改一下我的工作流」「帮我把这段代码改一下，顺便讲讲便签原理」「你觉得便签和备忘录哪个好用？我在考虑换成印象笔记」「便签的数据存在哪里？误删了能恢复吗」都会被整轮劫持进编辑流程——而那个流程会去改用户真实的便签。route 与 curate 的代价方向相反（curate 判错只多花点 token，route 判错是整轮被替换），所以这里 precision 第一、宁可漏接管。收紧办法不是加否定词表（列不完），而是要求**动词与便签在句法上真的挨着**：调参集与**未参与调参的泛化集**双双 precision 100% / recall 100%。顺带记下一条经验：**句法判定能靠正则、语义判定不能**——同一套方法下 route 泛化集 100%，curate 泛化集只有 42%，判定形态决定了正则的天花板。便签 1.0.4；check-plugins.js 增 route 语料 22 条（含零误接管硬门）+ 泛化集 13 条
